## Technical

### 1. Fix the failing gallery test (runs.json drift)
- **Impact:** 🔴 high · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `tests/gallery.test.mjs` hardcodes positional expectations for exactly 2 runs (`runs[0].evaluation.score === 58.8` at :17, `runs.map(model)` of length 2 at :22), but `src/data/runs.json` now has 3 runs (tooling added `gpt-5-6-luna-high` at index 0). The suite fails 4/5 tests today.
- **Proposal.** Stop pinning to array positions. Either select runs by `id` (`runs.find(r => r.id === 'gpt-5-6-sol-high')`) or move the asserted fixtures into a small test-owned JSON so gallery data churn can't break the suite.
- **Risks / trade-offs.** If the test is meant to guard the real shipped data, id-based lookup is the right fix; a separate fixture decouples but tests less of the real file.
- **Files.** `tests/gallery.test.mjs`, `src/data/runs.json`

### 2. One source of truth for the run shape (unify types + validate runs.json)
- **Impact:** 🔴 high · **Effort:** M · **Status:** ✅ accepted
- **Problem.** The run shape is described in three drifting places: `BenchmarkRun` inline in `src/App.tsx:32-58`, a parallel `PreviewRun` in `src/run-utils.ts:3-10`, and the untyped `src/data/runs.json`. New fields (`variant`, `target`, `benchmarkVersion`) were added by hand to the type and the data with nothing keeping them in sync.
- **Proposal.** Move `BenchmarkRun` into `run-utils.ts` (or a `src/types.ts`), make `PreviewRun = Pick<BenchmarkRun, …>`, import it in `App.tsx`, and add a test that validates `runs.json` against the type (lightweight: a `node:test` shape assertion, or a JSON Schema checked with a tiny validator).
- **Risks / trade-offs.** Low. Pure type/test consolidation; no runtime behavior change.
- **Files.** `src/App.tsx`, `src/run-utils.ts`, `src/data/runs.json`, `tests/gallery.test.mjs`

### 3. Resolve the v1/v2 rubric duplication
- **Impact:** 🟡 med · **Effort:** S · **Status:** ❌ dropped — v1 rubric is intentionally retained (evaluation/README.md:20)
- **Problem.** `evaluation/rubrics/v1.json` (3-stage) and `v2.json` (4-stage) both exist; `evaluate-run.mjs` always loads v2. The `gpt-5-6-sol-high` run carries `rubricVersion: "1.0.0"`, but no code path loads v1 to score it — so v1 is effectively dead weight unless re-scoring old runs is a real workflow.
- **Proposal.** Confirm nothing loads v1; if not, delete it and note the version on the run is historical only. If re-scoring matters, add an explicit `loadRubric(version)` in `evaluation/lib/scoring.mjs` instead of a hardcoded path.
- **Risks / trade-offs.** Deleting v1 loses the ability to reproduce historical 3-stage scores; keep it only if that's a goal.
- **Files.** `evaluation/rubrics/v1.json`, `evaluation/lib/scoring.mjs`, `.agents/skills/run-nord-benchmark/scripts/evaluate-run.mjs`

### 4. Extract shared CLI utilities from the three benchmark scripts
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `manage-run.mjs`, `evaluate-run.mjs`, and `verify-stage.mjs` each re-implement `parseArgs`, `findRepoRoot`, `readJson`, `writeJson` — and they're subtly inconsistent (e.g. `manage-run`'s `readJson` takes a fallback, others don't).
- **Proposal.** Add `.agents/skills/run-nord-benchmark/lib/cli.mjs` exporting the four helpers; import in all three scripts. ~80 lines deleted, one canonical behavior.
- **Risks / trade-offs.** Must preserve the fallback-arg variance carefully so callers don't change behavior.
- **Files.** `.agents/skills/run-nord-benchmark/scripts/{manage-run,evaluate-run,verify-stage}.mjs`, new `lib/cli.mjs`

### 5. Generate the gallery registry from per-run `run.json` (kill the dual write)
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** Every run's data lives twice: `runs/<id>/run.json` and an entry in `src/data/runs.json`. `manage-run.mjs`/`evaluate-run.mjs` write both on each change (`saveRun` at `manage-run.mjs:60-68`). Entries already drifted — older runs lack `benchmarkVersion`/`variant`/`target`. This dual source is exactly the "funky JSON" smell.
- **Proposal.** Make `runs/<id>/run.json` authoritative; add a `manage-run.mjs reindex` (or build step) that regenerates `src/data/runs.json` by globbing all `run.json` files. Gallery imports the generated index.
- **Risks / trade-offs.** Need to decide whether the index is committed (current) or built; keep committing it for the static deploy, just stop hand-maintaining it.
- **Files.** `src/data/runs.json`, `runs/*/run.json`, `.agents/skills/run-nord-benchmark/scripts/manage-run.mjs`, `evaluate-run.mjs`

### 6. Fold verify-stage's feature/check logic into the shared eval lib
- **Impact:** 🟡 med · **Effort:** M · **Status:** ⬜ deferred
- **Problem.** `verify-stage.mjs` hardcodes `REQUIRED_FEATURES` (:10-59) and runs test/typecheck/lint/build via `spawnSync`, duplicating the technical-check logic in `evaluate-run.mjs`. Two entry points, two arg parsers, two logging styles for closely related jobs.
- **Proposal.** Move the shared check runner into `evaluation/lib/` and have both scripts call it; consider moving `REQUIRED_FEATURES` into a small JSON keyed by phase so it lives beside the specs.
- **Risks / trade-offs.** `verify-stage` is invoked standalone by the skill (`test:verifier`, SKILL.md §2.3) — keep its CLI entry intact.
- **Files.** `.agents/skills/run-nord-benchmark/scripts/verify-stage.mjs`, `evaluate-run.mjs`, `evaluation/lib/`

### 7. Decide the fate of legacy 3-stage run support
- **Impact:** 🟡 med · **Effort:** M · **Status:** ⬜ deferred
- **Problem.** `App.tsx` carries `phaseNames` (4) + `legacyPhaseNames` (3) + `getPhaseName()` (:61-122) purely to render 3-stage runs. The catch: the *showcased* `gpt-5-6-sol-high` demo is itself a 3-stage run, so this can't simply be deleted.
- **Proposal.** Either (a) re-run/migrate the sol-high demo to the 4-phase format and delete the legacy branch, or (b) keep support but isolate it behind a single `getPhaseName`/`phaseCount` helper and a `legacy: true` flag on the run, instead of inferring from `stages.length === 3`.
- **Risks / trade-offs.** Option (a) regenerates a real benchmark artifact (cost/time); option (b) keeps the branch but makes it explicit and contained.
- **Files.** `src/App.tsx`, `src/data/runs.json`, `src/run-utils.ts`

## DevEx

### 9. Add GitHub Actions CI (typecheck, lint, test, build)
- **Impact:** 🔴 high · **Effort:** M · **Status:** ✅ accepted
- **Problem.** No `.github/workflows/` exists, so the gallery-test drift (idea 1), type errors, and lint/build regressions land silently. The benchmark prizes determinism but nothing enforces green on push.
- **Proposal.** Add `.github/workflows/ci.yml`: checkout → setup pnpm 11.7 + Node 24 → `pnpm install --frozen-lockfile` → `typecheck`, `lint`, `test`, `build`. Skip `fetch:reference` (network/copyright); ensure tests don't require it.
- **Risks / trade-offs.** Will go red until idea 1 is fixed — sequence it after. Verifier self-test may be slow; can be a separate job.
- **Files.** `.github/workflows/ci.yml` (new), `package.json`

### 10. Add an aggregate `pnpm test` script
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `package.json` has `test:gallery`, `test:evaluator`, `test:verifier` but no single `test`. Easy to run one suite and miss another (and CI needs one entry point).
- **Proposal.** Add `"test": "pnpm test:gallery && pnpm test:evaluator && pnpm test:verifier"`; document it as the canonical command in README/TESTING.
- **Risks / trade-offs.** Sequential is slightly slower; fine for this size.
- **Files.** `package.json`, `TESTING.md`, `README.md`

### 11. Pin Node with `engines` + `.nvmrc`
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `packageManager: pnpm@11.7.0` is pinned but Node isn't — no `engines` field, no `.nvmrc`. Contributors/CI can silently run a mismatched Node (ESM/TS behavior differences).
- **Proposal.** Add `"engines": { "node": ">=20" }` and a `.nvmrc` (`24`); reference it in CI's setup-node. (Raised earlier during the pnpm audit.)
- **Risks / trade-offs.** `engine-strict` could block contributors on older Node — keep the range permissive (`>=20`) rather than exact.
- **Files.** `package.json`, `.nvmrc` (new)

### 12. JSON Schema for the spec files, validated in tests
- **Impact:** 🟡 med · **Effort:** M · **Status:** ⬜ deferred
- **Problem.** `specs/*.json` (benchmark-phases, variants, visual, the 5 domain specs) are validated only by ad-hoc imperative assertions in `tests/specs.test.mjs`. New phases or hand-edits can introduce shape drift that the current tests don't catch — the other half of the "funky JSON" concern.
- **Proposal.** Author JSON Schemas for the spec families and validate each file against its schema in `tests/specs.test.mjs` (a tiny dependency-free validator, or `ajv`). Document the contract in `specs/README.md`.
- **Risks / trade-offs.** Schema authoring + a possible dep; scope to the specs that actually vary (variants, domain specs) rather than all eight at once.
- **Files.** `specs/*.schema.json` (new), `tests/specs.test.mjs`, `specs/README.md`
