## Technical

### 1. Memoize the leaderboard and isolate the toy-synth's high-frequency state
- **Impact:** 🔴 high · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `src/App.tsx` derives all leaderboard data inline every render — the `visibleRuns` sort (~481), `rankByRun`/tier loop (~489), `bestByTierPhase` (~501) — with zero `useMemo` (grep = 0 hits), then maps the full run list to JSX (~961-1098). The same component owns the playable toy synth whose handlers fire `setActiveNotes`/`setLastPlayed`/`setBend`/`setMod` on every pointer/key event (~547-653). Holding a chord or sweeping the pitch stick re-sorts and re-ranks every run and re-renders every `.run-row` at input-event rate.
- **Proposal.** Wrap `visibleRuns`/`rankByRun`/`bestByTierPhase` in `useMemo` keyed on the module-constant `runs` (compute-once). Extract the toy synth + `KeyboardRail` into a sibling with its own state so its updates don't re-render the leaderboard; `React.memo` the rail.
- **Risks / trade-offs.** The OLED "PROGRAM" readout (~911) reads both `activeNotes` and `runs`, so the split needs a small shared slice — get the boundary wrong and the readout desyncs. Otherwise low functional risk.
- **Files.** `src/App.tsx`

### 2. De-duplicate the run projection and telemetry field lists across the bench↔gallery boundary
- **Impact:** 🟡 med · **Effort:** S–M · **Status:** ✅ accepted
- **Problem.** The run→gallery shape is projected twice with independent defaults: `registryEntry` (`bench/lib/run/store.mjs:339-367`, writes `runs.json`) and `normalizeRunEntry` (`src/App.tsx:26-56`, reads it). The telemetry field list is written three times: `TELEMETRY_FIELDS` in `store.mjs:226`, `TELEMETRY_FIELDS` in `src/App.tsx:18-20`, and `TELEMETRY_FLAGS` in `bench/cli.mjs:60-68`. Adding a field means editing all of them in lockstep with no compiler link.
- **Proposal.** Define the telemetry field list once in a shared `.mjs` and import it into `store.mjs`/`cli.mjs`/the gallery (which already imports runtime helpers from `.mjs`). Share the raw/normalized run shape so the two projectors can't drift.
- **Risks / trade-offs.** The `.mjs`/`.ts` boundary needs a hand-written `.d.mts` (same pattern as `run-utils`), itself a drift risk (see #5). Low behavioral risk.
- **Files.** `bench/lib/run/store.mjs`, `bench/cli.mjs`, `src/App.tsx`, `src/types.ts`

### 3. Split the 1282-LOC `App.tsx` god-component
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `src/App.tsx` holds, in one file: 6 inline SVG icons (~192-234), three toy widgets (`PitchStick`/`ModWheel`/`KeyboardRail`, ~298-374), a full Web-Audio toy synth (voices/LFO/compressor, ~459-653), the entire leaderboard render, and four dialog overlays (~1145-1275). One component owns audio-graph lifecycle, URL/history sync, focus management, and layout.
- **Proposal.** Split into `components/icons.tsx`, `components/ToyKeyboard.tsx` (widgets + audio hooks), `components/RunList.tsx`, `components/dialogs/*`; keep `App.tsx` as composition + routing/dialog state. Pairs naturally with #1.
- **Risks / trade-offs.** The audio refs (`voicesRef`/`lfoRef`/`masterRef`) and the keyboard effect are tightly coupled; a bad extraction breaks voice cleanup on unmount (~796-812). Mostly mechanical otherwise.
- **Files.** `src/App.tsx` → new files under `src/components/`

### 4. Replace the preview iframe's fixed 12s failure timeout with a reachability probe
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `PreviewFrame` (`src/App.tsx:236-290`) declares failure via a 12s `setTimeout` if `onLoad` hasn't fired (~253-259) — cross-origin `onError` is unreliable, so this heuristic is the real error path. A slow-but-successful cold load at 13s shows a false "Preview failed"; a genuinely broken preview still makes the user wait the full 12s. `12000` is a magic constant unrelated to network reality.
- **Proposal.** Probe reachability with `fetch(src, { method: 'HEAD' })` (previews are same-origin under `/previews/`) to distinguish 404/500 from slow load; keep the timer only as a backstop for the truly-opaque case. At minimum name the constant and lengthen it for cold starts.
- **Risks / trade-offs.** HEAD adds a request per open and assumes same-origin (true for previews, not a cross-origin report frame). Keep the timer as fallback.
- **Files.** `src/App.tsx`

### 5. Close the `.d.mts` type-drift gap on the shared run/preview helpers
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** Canonical helpers live in `src/run-utils-runtime.mjs` (plain JS) with a hand-authored `src/run-utils-runtime.d.mts`. TS trusts the declaration without checking it against the `.mjs`, so a runtime signature change won't surface as a type error. The declaration already under-describes reality, forcing `App.tsx` to cast `initialViewer.run as RunEntry` (~446) and `viewer.run as RunEntry` (~698) — casts that hide genuine mismatches.
- **Proposal.** Either author the helpers in TS and emit types, or add a `// @ts-check`'d test that imports both and asserts conformance; tighten `parseViewerSearch`'s return type so the `as RunEntry` casts can be removed.
- **Risks / trade-offs.** The `.mjs` is deliberately plain JS so the Node test suite and the Vite app share one implementation without a build step; full TS conversion may require an emit step for the test runner. The check-only option avoids that.
- **Files.** `src/run-utils-runtime.mjs`, `src/run-utils-runtime.d.mts`, `src/run-utils.ts`, `src/App.tsx`

## UI/UX & Design

### 6. Fix the gallery focus ring — light amber fails visibility contrast on light surfaces
- **Impact:** 🔴 high · **Effort:** S · **Status:** ✅ accepted
- **Problem.** Every button/link/slider focus ring is `--amber` = `oklch(80% 0.17 75)` (`src/App.css:722, 340, 888, 1326`) against `--surface` `oklch(95%)` / white rows — well under WCAG 2.2's 3:1 focus-appearance minimum (SC 1.4.11 / 2.4.11). Keyboard users get a ring that's hard to locate, contradicting the PRODUCT.md "visible focus" AA target.
- **Proposal.** Use a darker high-contrast focus color on light surfaces (existing `--ink`/`--nord-red`, or a dedicated `--focus` ~`oklch(45-55%)`), or a double-ring that reads on both light rows and the red header. Keep amber only on dark chrome (toy panel, preview overlay).
- **Risks / trade-offs.** Red focus can be confused with brand red / error semantics — verify it reads on the red header and podium-tinted rows. One token may not be optimal on both dark toy and light index; may need two.
- **Files.** `src/App.css` (`:root` tokens, all `:focus-visible` rules)

### 7. Make the mobile keyboard-rail keys meet minimum touch-target size
- **Impact:** 🔴 high · **Effort:** M · **Status:** ✅ accepted
- **Problem.** The rail renders 28 white keys edge-to-edge (`src/App.tsx:76`) in a container that collapses to `calc(100% - 32px)` at ≤640px (`src/App.css:1370`). On a 375px phone that's ~12px per white key; black keys are 54% of that (`src/App.css:680`) ≈ 6-7px. WCAG 2.5.8 wants ≥24×24px, so keys are effectively un-tappable and adjacent keys misfire. QWERTY hint chips are also hidden here (`:1386`), removing the rail's only affordance where it's hardest to use.
- **Proposal.** On touch/narrow viewports, either show ~2 octaves with horizontal scroll/octave paging so each white key clears ~24-30px, or make the rail horizontally scrollable at a fixed comfortable width. Consider hiding it below a threshold with a "play on desktop" hint (mirror the showcase `screen-notice`).
- **Risks / trade-offs.** Horizontal scroll competes with page scroll (set `touch-action`/overflow carefully). Fewer keys changes the hero's visual proportion; paging adds state.
- **Files.** `src/App.tsx` (KeyboardRail, headerKeys), `src/App.css` (`.toy-keys`, `.white-key`, `.black-key`, mobile media query)

### 8. Give small gallery controls a ≥24px hit area
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** The protocol info button is 16×16 (`src/App.css:873`), the details chevron 28×28 (`:1010`), phase-switch buttons `min-width:34px` with no min-height (`:1193`), octave buttons `clamp(19px…28px)` (`:351`). Several fall under WCAG 2.5.8's 24px floor and the 16px info button has no hit-padding — fiddly on touch.
- **Proposal.** Add an invisible hit area (padding or an `::before` overlay) to reach ≥24×24 (ideally ~44px on touch) without changing visual size — the pattern the showcase already uses for `.midi-transport-bar::before` (`showcase/src/styles.css:6505`). Floor octave and phase-switch buttons at 24px min-height.
- **Risks / trade-offs.** Enlarged hit areas can overlap neighbors in the dense tower/phase-switch rows — verify they don't swallow adjacent clicks. Some controls qualify for 2.5.8's inline/essential exceptions, so this is polish, not a hard failure everywhere.
- **Files.** `src/App.css` (`.protocol-info-btn`, `.row-info`, `.phase-switch button`, `.octave-buttons button`)

### 9. Unify the showcase's split focus-ring color (blue vs amber, one rule already dead)
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** Instrument controls focus blue `#57b7ff` (`showcase/src/styles.css:779, 1081, 2369, 6343`) while chrome/overlays focus amber `#d8a03c` (`:416, 1946, 6046…`). Worse, `.knob/.encoder:focus-visible` sets amber (`:1944`), but knobs carry `role="slider"` (`controls.tsx:130`) and `[role="slider"]:focus-visible` (`:2367`) sets blue with equal specificity but later source order — so the amber knob rule is dead and knobs actually focus blue. The focus language across "one instrument" is inconsistent and partly unintended.
- **Proposal.** Define one `--focus-ring` custom property, use it everywhere, delete the overridden `.knob/.encoder` amber rule. If a deliberate two-tier system (instrument vs chrome) is wanted, document it and make it consistent.
- **Risks / trade-offs.** Low, purely visual. Confirm the chosen color clears 3:1 against both the dark keybed and light plates.
- **Files.** `showcase/src/styles.css`, `showcase/src/components/controls.tsx`

### 10. Extract the duplicated chassis-red palette into shared tokens
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** The chassis reds `#a63440 / #912a35 / #892531 / #78202b` appear as raw hex in the gallery toy (`src/App.css:184`) and again in the showcase (`showcase/src/styles.css:82-86`); end-cheek reds `#a02635 / #701e29` are duplicated too (`src/App.css:613` vs `styles.css:601`). The gallery's own `--nord-red` is oklch and the toy chassis doesn't use it. PRODUCT.md principle 2 depends on both surfaces agreeing on red, but there's no shared source, so a tweak to one silently diverges.
- **Proposal.** Extract gradient stops into named tokens (`--chassis-hi/-mid/-dark/-deep`, `--cheek-hi/-lo`) defined once and referenced in both stylesheets. Pick one color space (repo is mid hex→oklch migration) and normalize.
- **Risks / trade-offs.** The two surfaces are separate build roots, so a truly shared file needs a small import step or a copied partial (which re-drifts unless linted). hex→oklch can shift color subtly — diff visually.
- **Files.** `src/App.css`, `src/index.css`, `showcase/src/styles.css`

## Product Features

### 11. Surface the five honest run groups the product promises
- **Impact:** 🔴 high · **Effort:** M · **Status:** ❌ rejected
- **Problem.** PRODUCT.md principle 4 promises "official, exploratory, legacy, partial, and invalid runs stay visible in distinct groups," but `getResultClass()` (`src/App.tsx:183`) returns only `legacy` vs `current`, and `src/types.ts:64` types `status` as `'in-progress' | 'complete' | 'legacy'`. The harness has a richer `failed`/`invalid`/`budget-exceeded` vocabulary (`store.mjs:324`) that never reaches the UI, so failed/aborted/exploratory runs have no honest home.
- **Proposal.** Add an explicit `group` field to `run.json`/`registryEntry` (official | exploratory | partial | invalid | legacy), project it into `runs.json`, and drive the run-index headings (`App.tsx:974`) and tiering off it instead of the boolean `legacy`. Partial = target phase unreached; invalid = sealed but gate/honesty failure; exploratory = off-protocol.
- **Risks / trade-offs.** Must not silently re-tier existing sealed runs — default every current run to `official`, require explicit opt-out. `normalizeRunEntry` (`App.tsx:26`) needs a back-compat default.
- **Files.** `src/App.tsx`, `src/types.ts`, `bench/lib/run/store.mjs`, `src/data/runs.json` (regenerated), `PRODUCT.md`

### 12. Show per-category scores in the run row (without opening the HTML report)
- **Impact:** 🔴 high · **Effort:** M · **Status:** ❌ rejected
- **Problem.** The scorer already computes per-category scores (`cli.mjs:248` `categoryScores`; `scoring.mjs:104` per-criterion `rating`/`score`/`evidence`), but `registryEntry` (`store.mjs:360`) discards all of it, projecting only `{number, status, score, reportPath}` per stage. To see *why* a run scored 66.8 you must open the full static HTML iframe (`App.tsx:1275`). The gallery's job is comparison, yet the axes (visual vs audio vs engineering) are invisible in the index.
- **Proposal.** Project `categoryScores` into each stage entry in `runs.json` and render a small segmented bar or hover breakdown in the phase `sector` cell (`App.tsx:1041`). Optionally a re-rank-by-category toggle.
- **Risks / trade-offs.** Category ids/weights differ across rubric versions; legacy runs render `—`. Keep to the ~5 category rollups (not full criterion evidence) to avoid bundle bloat.
- **Files.** `bench/lib/run/store.mjs`, `src/types.ts`, `src/App.tsx`, `src/data/runs.json`

### 13. Add filter + search + sort controls over the run index
- **Impact:** 🔴 high · **Effort:** M · **Status:** ❌ rejected
- **Problem.** `App.tsx:481` hard-codes a single sort (tier → score → recency) and offers no filter/search. Runs already span harnesses (`opencode`, `Codex`, Claude Code) and 9+ entries; there's no way to say "only Codex runs" or find a model by name, even though `harness`/`model`/`protocolVersion`/`variant`/telemetry are all present on `RunEntry`.
- **Proposal.** Add a compact control strip above `.run-index` (`App.tsx:954`): text filter on model/title, harness pills, protocol-version filter, sort dropdown. Persist selection in the URL query (reuse `parseViewerSearch`/`createViewerUrl`) so a filtered view is shareable.
- **Risks / trade-offs.** Keep it one restrained instrument-panel row — the PRODUCT.md anti-references warn against SaaS-dashboard sprawl. Sort-by-cost is misleading while many runs have `costUsd: null`; null must sort last. (Note: a full sortable *table view* and $-per-score column were previously rejected — this keeps the existing rows and adds filter/search, not a table reformat.)
- **Files.** `src/App.tsx`, `src/run-utils.ts` / `run-utils-runtime.mjs`, `src/App.css`

### 14. Add an audio-provenance / honesty badge from IMPLEMENTATION_DETAILS
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** The honesty contract's central artifact — `IMPLEMENTATION_DETAILS.json`, truthfully declaring audio sources — is collected (`collectImplementationDetails`, `cli.mjs:158`) and rendered into the static HTML report (`report.mjs:82`), but is absent from the gallery index. A user comparing runs can't see at a glance which recreations use recorded samples vs. generated buffers — exactly the distinction the contract exists to keep honest.
- **Proposal.** Project a compact provenance summary (recorded / generated / hybrid + library count) into `runs.json` and show a small honest badge on the run row. Surfaces existing truthful data only — changes no rule, re-scores nothing.
- **Risks / trade-offs.** Must render exactly what the declared details say and never infer/upgrade a claim; legacy runs lacking the file show nothing. Slight `runs.json` growth.
- **Files.** `bench/lib/run/store.mjs` (or a sibling projector), `bench/lib/implementation-details.mjs`, `src/types.ts`, `src/App.tsx`

### 15. Add evaluator-panel scaffolding + inter-evaluator agreement
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** Panels merge at score time (`cli.mjs:206` scans `assessment(.\d+)?.json`; `mergeAssessments` takes the per-criterion median), but there's no ergonomics for *running* a panel: no command to scaffold `assessment.2.json`, and nothing surfaces disagreement. The median silently discards spread, so a 0/4 split looks identical to a unanimous 2 — noise is invisible to evaluators (a named user group in PRODUCT.md).
- **Proposal.** Add `bench score <id> --phase N --add-evaluator` to clone a blank assessment into the eval workspace, and compute+store a per-criterion agreement stat (range/stdev) alongside the median in the archived assessment and report. Show "panel of N, agreement X" on scored runs.
- **Risks / trade-offs.** Must not change the median-based score itself (protocol-comparison-critical) — agreement is additive metadata only. Extra evaluator runs cost agent time; keep single-evaluator the default.
- **Files.** `bench/cli.mjs`, `bench/lib/eval/workspace.mjs`, `bench/lib/eval/scoring.mjs`, `bench/lib/eval/report.mjs`



### 16. Add showcase gates to CI
- **Impact:** 🔴 high · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `.github/workflows/ci.yml` runs only root `pnpm typecheck/lint/test/build`. `showcase/` — the flagship, deployed instrument with 50 Vitest files, a `verify:layout` gate, and its own lockfile — has zero CI coverage. CLAUDE.md says it "must keep passing its own gates," but nothing enforces it; regressions only surface manually.
- **Proposal.** Add a job (or steps) that runs `pnpm -C showcase install --frozen-lockfile` then `typecheck`/`lint`/`test`/`build`/`verify:layout`, gated on `showcase/**` changes. Install separately since showcase isn't a workspace.
- **Risks / trade-offs.** Longer CI; showcase pulls audio-sample/ffmpeg-static deps (heavier cache). `verify:layout` may be flaky if it needs fetched samples — check `scripts/verify-layout.mjs` inputs first.
- **Files.** `.github/workflows/ci.yml`

### 17. Declare `@types/node` in the starter and delete the ambient-copy hack
- **Impact:** 🔴 high · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `bench/starter/package.json` omits `@types/node`, yet starter configs and candidate code typecheck against it ambiently via repo-root `node_modules`. `evaluate.mjs` (`ambientNodeTypes`/`provisionNodeTypes`, ~80-100) exists solely to re-inject it into the out-of-repo gate copy — and returns `null` (silently skipping) if the repo root ever lacks it, which would fail an honest candidate with false type-error caps.
- **Proposal.** Add `@types/node` (`^24`, matching `.nvmrc`) to `bench/starter/package.json` and regenerate its lockfile; then delete the ambient hack and the Docker `/ambient/node` mount so gates are self-contained.
- **Risks / trade-offs.** Regenerating the starter lockfile shifts the template every future candidate clones — re-verify a sample seal. Legacy sealed runs re-scored later still lack the dep, so keep the fallback for legacy artifacts or gate removal on schema version.
- **Files.** `bench/starter/package.json`, `bench/starter/pnpm-lock.yaml`, `bench/lib/eval/evaluate.mjs`

### 18. De-brittle the registry snapshot test
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `tests/gallery.test.mjs`'s "keeps the current GPT-5.6 runs" test hardcodes run IDs, `startedAt` prefixes (`/^2026-07-09T/`), and `claude-fable-5.score === 96.8`, all read from generated `src/data/runs.json`. Any legitimate run add/remove/rescore breaks it — matching the known "legacy-runs test fails on some machines" symptom whenever the local registry diverges from the frozen snapshot.
- **Proposal.** Keep the structural/projection invariants (already covered by the RunEntry-conformance test + synthetic `pianoOnly` fixture) and either drop the content-snapshot assertions or move them behind an explicit fixture file rather than the live registry.
- **Risks / trade-offs.** Loosening loses a guard against accidental deletion of canonical runs; mitigate by asserting invariants ("no legacy run has a null score") instead of exact values.
- **Files.** `tests/gallery.test.mjs`

### 19. Reconcile the conflicting Node-version declarations
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** Three sources disagree: `.nvmrc`=24; `.claude/launch.json` and CLAUDE.md hardcode `v24.18.0` (breaks for any other 24.x patch); `package.json` `engines.node: ">=20"` is looser than reality (oxlint needs `^20.19||>=22.12`, node-web-audio-api needs `>=22`). A contributor on Node 20.0-20.18 or a different 24.x patch hits confusing failures the docs blame on "Node 18."
- **Proposal.** Tighten root `engines.node` to `>=22` (or `^24`), add `engine-strict`. Replace the hardcoded `v24.18.0` in `launch.json` with a version-agnostic invocation (`nvm use` / `$(nvm which 24)`) and update CLAUDE.md. Optionally a `doctor`/`preinstall` check of `process.version` vs `.nvmrc`.
- **Risks / trade-offs.** Stricter engines can block valid-but-older setups — pick the floor deliberately. Changing `launch.json` risks preview servers not starting if nvm isn't sourced in the non-interactive shell — test both `dev` and `showcase`.
- **Files.** `package.json`, `.claude/launch.json`, `CLAUDE.md`, `.nvmrc`

### 20. Add a subagent-JSONL telemetry parser to stop hand-entered token overcounts
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `bench seal`/`telemetry` accept usage only via manual flags (`TELEMETRY_FLAGS` in `cli.mjs`). The Claude Code `subagent_tokens` notification reports final *context size*, not output tokens, so hand-entered numbers overstate usage (observed ~2.1× on a fable-5 run); correct figures require summing subagent JSONLs, which nothing in-repo does.
- **Proposal.** Add `bench telemetry --from-jsonl <path>` (or `scripts/parse-subagent-telemetry.mjs`) that reads subagent JSONL transcripts, recomputes input/output/reasoning tokens + cost, and feeds `recordTelemetry`. Document the `subagent_tokens` gotcha in BENCHMARK.md.
- **Risks / trade-offs.** The JSONL schema is external and can shift across Claude Code versions — the parser needs defensive handling and a clear failure mode, not silent miscounts. Keep manual flags as fallback.
- **Files.** `bench/cli.mjs`, new `scripts/parse-subagent-telemetry.mjs` or `bench/lib/`, `BENCHMARK.md`
