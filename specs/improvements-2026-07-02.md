## Technical

### 1. Iframe preview error handling in the gallery
- **Impact:** 🟡 med · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `src/App.tsx:567-572` and `:589` render preview/report iframes with no fallback. A malformed preview URL or missing published build fails silently — the user sees an empty pane with no explanation.
- **Proposal.** Add an `onError`/load-timeout fallback state on the iframe container that shows a short factual message ("Preview failed to load") with the attempted path, styled like existing status text.
- **Risks / trade-offs.** Iframe error signaling is limited cross-origin; detection may need a load timeout heuristic, which can false-positive on slow connections.
- **Files.** `src/App.tsx`, `src/App.css`

### 2. Deduplicate run-utils between TypeScript and runtime JavaScript
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `src/run-utils.ts` and `src/run-utils-runtime.mjs` contain identical logic (`getRunTitle`, `floorScore`, `getPreviewPath`, `getLatestPhase`, `parseViewerSearch`, `createViewerUrl`, `clearViewerUrl`). Two copies drift silently.
- **Proposal.** Make one implementation the single source (e.g. keep the `.mjs`, add a `.d.ts`, or have tests import the TS build) so App.tsx and `tests/gallery.test.mjs` share one module.
- **Risks / trade-offs.** Must work in both Node (node:test) and browser (Vite) contexts; small build-config churn.
- **Files.** `src/run-utils.ts`, `src/run-utils-runtime.mjs`, `tests/gallery.test.mjs`

### 3. Parallelize and cache registry reindex
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `bench/lib/run/store.mjs:258-268` (`reindexRegistry`) does a serial `readdirSync` + `readJson` per run on every `pnpm dev`/`pnpm build` (via pre-scripts). Cost grows linearly with `runs/` and is already a fixed tax on every dev start.
- **Proposal.** Read run.json files concurrently with `fs.promises` + `Promise.all`, and skip unchanged runs via an mtime cache so incremental reindex is near-instant.
- **Risks / trade-offs.** Mtime caching can go stale if run files are edited without touching mtime (rare); adds a small cache file to manage.
- **Files.** `bench/lib/run/store.mjs`

### 4. Replace blocking spawnSync in verify/evaluate with async spawn
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `bench/lib/eval/evaluate.mjs:34` and `bench/lib/run/verify.mjs:75` run candidate `test`/`typecheck`/`lint`/`build` via `spawnSync` with 240s timeouts — the CLI blocks with no streamed output and no graceful cancellation (Ctrl-C can leave child processes orphaned).
- **Proposal.** Switch to async `spawn` wrapped in a timeout promise; stream output as progress, forward SIGTERM to children, keep exit-code semantics identical.
- **Risks / trade-offs.** More complex output collection; callers must become async — a mechanical but cross-cutting change to the seal/score paths.
- **Files.** `bench/lib/eval/evaluate.mjs`, `bench/lib/run/verify.mjs`, `bench/cli.mjs`

### 5. Validate viewer URL search parameters
- **Impact:** ⚪ low · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `src/run-utils.ts:33-44` (`parseViewerSearch`) coerces `phase` with `Number()` and accepts any `run` string without bounds/shape checks; garbage URLs fall through to undefined behavior rather than an explicit fallback.
- **Proposal.** Validate phase ∈ {1..4} and run id against `/^[a-z0-9-]+$/`; return null on invalid input so the existing `getLatestPhase` fallback handles it. Mirror in the runtime copy (or land after idea 2).
- **Risks / trade-offs.** Stricter parsing could reject previously tolerated bookmark URLs.
- **Files.** `src/run-utils.ts`, `src/run-utils-runtime.mjs`, `tests/gallery.test.mjs`

### 6. Guard header-keyboard audio cleanup
- **Impact:** ⚪ low · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `src/App.tsx:199-383` manages the mini-keyboard's AudioContext/OscillatorNodes; the unmount cleanup (`:377-383`) calls `oscillator.stop()` without try/catch, which throws if a voice already ended via its `onended` callback.
- **Proposal.** Wrap stop calls in try/catch and mark ended voices via the `onended` flag instead of relying on Map membership alone.
- **Risks / trade-offs.** Minimal; purely defensive.
- **Files.** `src/App.tsx`

### 7. Consistent null-safety for run entry fields in gallery rendering
- **Impact:** ⚪ low · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `src/App.tsx:470-488` guards `previewPath`/`reportPath` but assumes other fields (model, phase metadata) always exist; legacy-schema runs make this fragile and the optional chaining is inconsistent.
- **Proposal.** Normalize entries at load time (small factory/validator over `src/data/runs.json`) so the render path can assume a complete `RunEntry`; tighten `src/types.ts` accordingly.
- **Risks / trade-offs.** May surface missing data in old runs that was previously silently blank — arguably a feature.
- **Files.** `src/App.tsx`, `src/types.ts`

### 8. Timeout and retry for reference fetches
- **Impact:** ⚪ low · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `bench/lib/fetch-reference.mjs:44` downloads the Nord manual and photos from external servers with no timeout — a CDN stall hangs `pnpm bench fetch` indefinitely.
- **Proposal.** Add AbortController-based timeout (60s default, `--timeout` flag) plus one or two retries with backoff for transient failures.
- **Risks / trade-offs.** Retries can mask persistent network problems; keep the failure message explicit.
- **Files.** `bench/lib/fetch-reference.mjs`, `bench/cli.mjs`

### 9. Distinguish crypto errors from invalid signatures in middleware
- **Impact:** ⚪ low · **Effort:** S · **Status:** ✅ accepted
- **Problem.** `middleware.js:44-60` (`isValidSession`) swallows all errors from `crypto.subtle.verify` and returns false — a genuine crypto/config failure is indistinguishable from a bad cookie in the logs.
- **Proposal.** Catch and log unexpected crypto errors (with stack) separately from expected invalid-signature results, keeping the response identical (fail closed, no timing changes).
- **Risks / trade-offs.** Must not vary response timing or content between the two paths; logging only.
- **Files.** `middleware.js`, `tests/middleware.test.mjs`

### 10. Single source of truth for protocol constants in the gallery
- **Impact:** ⚪ low · **Effort:** M · **Status:** ✅ accepted
- **Problem.** `src/App.tsx:18-24` hardcodes `phaseNames`, `legacyPhaseNames`, `v2PhaseNames` alongside note/knob constants, duplicating protocol facts that already live in `specs/benchmark-phases.json` — a protocol rename requires edits in multiple places.
- **Proposal.** Derive phase names/labels from `specs/benchmark-phases.json` at reindex time (emit into `src/data/runs.json` or a small generated constants module), leaving purely presentational constants in App.tsx.
- **Risks / trade-offs.** Legacy/v2 naming isn't in the current spec file, so it needs an explicit legacy mapping; adds a generation step.
- **Files.** `src/App.tsx`, `specs/benchmark-phases.json`, `bench/lib/run/store.mjs`

## Product Features

### 11. Telemetry leaderboard table view
- **Impact:** 🔴 high · **Effort:** M · **Status:** ❌ rejected
- **Problem.** `src/App.tsx:443-527` lists runs chronologically and renders telemetry as prose (`formatTelemetry`, `:85-98`). Answering "which model finished Phase 2 fastest per dollar?" requires manually cross-referencing `src/data/runs.json` entries.
- **Proposal.** Add a toggleable sortable table view over the current result group: model, score, wall time, cost, tokens, plus a derived score-per-dollar column. Keyboard-sortable headers, honest grouping preserved (official/exploratory/legacy stay separate).
- **Risks / trade-offs.** Column density at mobile widths; derived metrics are misleading when telemetry is partial — must render gaps honestly, not as zeros.
- **Files.** `src/App.tsx`, `src/types.ts`, `src/App.css`

### 12. Side-by-side run comparison view
- **Impact:** 🔴 high · **Effort:** M · **Status:** ❌ rejected
- **Problem.** The viewer (`src/App.tsx:188-223`, `parseViewerSearch`) shows one run at a time; comparing two models' Phase-N artifacts means bouncing between previews and losing context.
- **Proposal.** Comparison mode: select two runs, render both previews side-by-side at the same phase with their telemetry deltas (score, cost, wall time) in a compact header. Encode both runs in the URL for shareability within the private deployment.
- **Risks / trade-offs.** Two live instrument iframes is heavy (two AudioContexts); URL-routing changes touch `parseViewerSearch`/`createViewerUrl`; narrow viewports need a stacked layout.
- **Files.** `src/App.tsx`, `src/run-utils.ts`, `src/run-utils-runtime.mjs`, `src/types.ts`, `src/App.css`

### 13. Cross-phase regression flagging
- **Impact:** 🔴 high · **Effort:** M · **Status:** ❌ rejected
- **Problem.** BENCHMARK.md requires later phases not to regress earlier ones (`regression.phase1`, etc.), but the gallery shows per-phase scores with no delta — a run whose Phase 1 criteria dropped between evaluations isn't flagged anywhere in `src/App.tsx`.
- **Proposal.** At reindex time, compute per-run phase-score deltas from the sealed evaluations and surface a small severity marker in the run row ("Phase 3 −8 vs Phase 2") linking to the relevant report. Text plus color, per accessibility principles.
- **Risks / trade-offs.** Distinguishing evaluation noise from true regression needs a threshold; false alarms erode trust in the marker.
- **Files.** `bench/lib/run/store.mjs`, `src/App.tsx`, `src/types.ts`

### 14. Feature-matrix pass/fail overlay per phase
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** Each run ships `tests/feature-matrix.json` mapping required feature IDs to test files, and verification results are sealed per stage — but the gallery only shows an aggregate score. Drilling into *which* feature (e.g. `effects.routing`) failed means opening raw JSON.
- **Proposal.** A modal/panel from the preview header listing the phase's feature IDs with pass/fail state from the sealed verification, grouped by rubric category with small aggregate bars.
- **Risks / trade-offs.** Verification schema varies across protocol versions; legacy runs must degrade to "not available" rather than guess.
- **Files.** `src/App.tsx`, `bench/lib/run/store.mjs`, `src/types.ts`, `src/App.css`

### 15. Per-phase telemetry breakdown in the viewer
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** `src/types.ts:24-31` and `formatTelemetry` (`src/App.tsx:85-98`) expose run-level telemetry only, though wall time is recorded per phase by the bench CLI. You can't see that Phase 3 is the wall-clock/cost bottleneck of a run.
- **Proposal.** Show a compact per-phase breakdown (time, cost, tokens where present) in the viewer header or run details, with cumulative totals; nulls render as "—".
- **Risks / trade-offs.** Sparse for old runs; needs the reindex projection to carry stage-level telemetry into `runs.json`.
- **Files.** `bench/lib/run/store.mjs`, `src/App.tsx`, `src/types.ts`

### 16. Model × phase performance grid
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** With runs multiplying across models and targets (`runs/` already holds claude-fable-5, gpt-5-6-luna/-sol, haiku variants), the flat list in `src/App.tsx` makes "who has completed what" hard to read at a glance — PRODUCT.md principle 1.
- **Proposal.** Optional grid view: rows = models, columns = phases; each cell shows best score + status, click-through to the viewer. Top score per column highlighted, missing cells honestly empty.
- **Risks / trade-offs.** Overlaps partially with the leaderboard (idea 11) — if both are accepted, build as two tabs of one view. Needs a rule for multiple runs of the same model (best vs latest).
- **Files.** `src/App.tsx`, `src/App.css`, `src/types.ts`

### 17. Cost actuals dashboard by model and phase
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** Cost/token telemetry is captured at seal time (`bench/cli.mjs` telemetry flags) and stored in run.json, but nothing aggregates it — total spend and per-model averages are invisible.
- **Proposal.** A small dashboard section: per-model average cost and wall time per phase, plus a total-spend line, computed from `src/data/runs.json` at render time. Plain factual numbers, no charts required.
- **Risks / trade-offs.** Averages over few runs are noisy; partial telemetry must be excluded from averages and labeled, not zero-filled.
- **Files.** `src/App.tsx`, `src/App.css`

### 18. Single-run export bundle
- **Impact:** 🟡 med · **Effort:** M · **Status:** ✅ accepted
- **Problem.** Sharing a run for external review means hand-collecting `runs/<id>/run.json`, evaluation reports, and the published preview from `public/reports|previews/`.
- **Proposal.** A `pnpm bench export <run-id>` CLI command producing a ZIP with run.json, evaluations, the static report, and preview build, plus a manifest (timestamp, protocol version). CLI-first fits the terminal-centric user in PRODUCT.md.
- **Risks / trade-offs.** Preview builds can be large; must never bundle gitignored `reference/` material (copyright).
- **Files.** `bench/cli.mjs`, `bench/lib/run/store.mjs` (new `bench/lib/run/export.mjs`)

### 19. Run notes and reclassification via the CLI
- **Impact:** 🟡 med · **Effort:** M · **Status:** ❌ rejected
- **Problem.** Run classification (`kind`, `comparable`, `reason` in `runs/<id>/run.json`) drives the gallery's honest grouping, but changing it or attaching evaluator notes requires hand-editing sealed JSON — error-prone next to sealed fields.
- **Proposal.** `pnpm bench annotate <run-id> --kind exploratory --note "..."` that validates against `bench/schemas/run.schema.json`, touches only classification/notes fields, and reindexes. Surface the note in the run row tooltip/details.
- **Risks / trade-offs.** Must hard-fail on any attempt to touch sealed artifact/evidence fields; adds schema surface.
- **Files.** `bench/cli.mjs`, `bench/lib/run/store.mjs`, `bench/schemas/run.schema.json`, `src/App.tsx`

### 20. Phase evolution timeline per run
- **Impact:** ⚪ low · **Effort:** M · **Status:** ❌ rejected
- **Problem.** Phases are cumulative (each starts from the previous sealed artifact) but the gallery presents them as independent tabs — what Phase 2 *added* over Phase 1 (features, score movement, time) isn't visible.
- **Proposal.** A compact per-run timeline in the details view: for each phase transition, feature IDs added (from the phase spec), score delta, and wall time, sourced from sealed verifications and evaluations.
- **Risks / trade-offs.** Requires consistent digests/verifications across phases; low payoff until multi-target runs are common.
- **Files.** `src/App.tsx`, `bench/lib/run/store.mjs`, `src/types.ts`
