Phase 1

Complete surface and basic piano

Audio strategy
Live synthesis only. One piano-like voice is computed sample by sample by a TypeScript DSP kernel (additive synthesis: a bank of exponentially decaying sine partials per note). The kernel runs in an AudioWorklet; if the worklet cannot load, the same kernel runs in a ScriptProcessorNode and the status reads 'Fallback'. No recorded samples are bundled, fetched, or played, and no audio buffers are generated or stored.
Generated sound sources
  • Basic Piano partial bank — Per note: up to 32 sine partials at stretched (inharmonic) frequencies, amplitudes shaped by strike position and a velocity-dependent spectral slope and felt lowpass, each decaying exponentially with higher partials decaying faster; the lowest 6 partials also carry a slower, 0.9-cent-sharp aftersound component for two-stage decay and beating. Attack ramp of 1-4 ms, pitch-dependent damper release, mild note-dependent stereo pan.
  • Hammer noise burst — A 12 ms decaying burst of lowpassed pseudo-random noise per strike, generated per sample by a xorshift32 generator seeded from the note number and strike order (deterministic). It is computed live; it is not a noise buffer.

Piano library and working effects

Audio strategy

  • Synth Marimba — Wooden bar modes at 1 : 3.93 : 9.2 with a short ring, plus a short mallet noise burst.
  • Sympathetic string resonance — Simulated, not sampled. When a note is struck, each undamped string (a held key, or with the pedal down the octave/fifth/fourth relatives of the struck note) that shares a partial with it gets one slowly rising, decaying sine at the shared frequency, damped when that string is damped. The upstream pedal-down resonance recordings are not used.

A synced Synth LFO, arpeggiator, Delay, or Mod 1 has its rate derived from the tempo and the subdivision its knob selects (1/2, 1/4, 1/4T, 1/8, 1/8T, 1/16, 1/16T) when the sound state is derived; the kernel receives plain rates in Hz. Keyboard Sync restarts a synced layer when a key is played after all keys were up.
  • Signal path, per Piano layer: voices -> Piano Timbre EQ -> Mod 1 -> Mod 2 -> Delay -> Amp Sim/EQ (or LP24/HP24 filter) -> Compressor -> Reverb -> Rotary (when routed) -> layer level; then both layers -> sum -> master gain (Master Level) -> soft limiter -> one output node -> AudioContext.destination. There is exactly one connection to the destination and nothing bypasses the master stage.
  • The Rotary has one shared rotor (speed, acceleration, angles, drive setting). Each routed layer passes through its own crossover and delay lines driven by that rotor, so that the layer level can follow the Rotary as the documented order requires; two routed layers therefore overdrive separately rather than as a sum.
  • Group and Global are implemented as shared settings: an edit is applied to every chain in the group (or to every chain for a Global unit), and entering the mode copies the focused chain's settings to the others. Each layer still runs its own instance of the unit, before its level fader; a Global Reverb is not moved after the Rotary (the effects spec excludes that nuance).
  • Polyphony is 48 voices per layer (a Unison note uses 2 or 3) with deterministic stealing: released voices first, then pedal-held, then held keys; oldest strike first within a class.
  • Velocity response: loudness follows velocity^1.7 after the KB Touch curve; Dyn Comp reduces that exponent. Within one velocity layer the softer end is slightly lowpassed so adjacent layers meet smoothly.
  • The app decodes FLAC itself (src/audio/library/flac.ts) instead of calling decodeAudioData, so the same bytes give the same samples in every browser and in the tests.
  • Sample files are fetched by relative path from the build output (public/samples -> dist/samples). No network host is contacted. Opening dist/index.html from file:// blocks both the worklet and the sample fetches in most browsers; the app then says so and plays the labelled fallback, or reports that it is silent.

  2. minor forbiddenDetection's displayElement rule is ambiguous for printed group legends: The spec defines a displayElement partly as an element rendering multi-character alphanumeric text on a dark fill, excluding a control's own printed legend. The panel's group-name chips (class 'lbl lbl--cut-dark', e.g. MOD 1, DELAY, COMP, REVERB, AMP SIM/EQ, TO ROTARY in the effects band and ORGAN MODEL, VIB/CHORUS, B3 PERCUSSION in the organ band) carry their own rgb(60,66,77) fill, so a hyper-literal reading would count 7 of them in the effects band and fire the forbidden 'OLED display' rule there. I scored forbiddenPresent = 0 because the reference photograph carries the same printed group names in the same notched rules, and the rule's own note states the effects band carries no display on the photograph - so the exclusion must cover printed legends generally, not only a control's own. Under the alternative reading the count would be 1 (effects). Performance, where the rule would also apply, has no such chip, so that band is 0 either way.
  3. minor data-section attribute collides between layout sections and the Program OLED: src/ui/Instrument.tsx:80 puts data-section={geometry.id} on each of the six layout <section> elements, while src/ui/Oleds.tsx:166 puts data-section={state.ui.section} on the Program OLED to record which engine the display is describing. Purely a DOM-hygiene issue - no visual or behavioural effect - but it silently breaks any section-attribution tooling, including a naive landmark audit.
