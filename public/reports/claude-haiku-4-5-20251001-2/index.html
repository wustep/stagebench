Phase 2

Piano instrument

24/100 · incomplete

This is barely a Phase 1 surface with an unwired audio module bolted on. Mechanical gates are green (67 tests, typecheck, lint, build all pass), but the tests validate hardcoded data literals and Web Audio primitives, not the rendered artifact. In the live app the 73-key keyboard does NOT render: only ~8 white and ~6 black keys appear because Keyboard.tsx uses a fixed 14-character pattern string. Every section 'control' is a plain text <span> label, so there are zero knobs, drawbars, faders, buttons, LEDs, or OLED displays; none of the piano controls (type/model/touch/compression/timbre/unison/volume/reverb/sustain) are rendered or wired to audio. The sound source is a placeholder Tone.PolySynth triangle oscillator (self-described as 'FM Synthesis'), not credible piano material, failing hard gate 1. Pointer input is dead in the running app because the InputHandler prop is undefined on the only render pass. Only the computer-keyboard path can produce sound. The biggest gaps: the keyboard render is broken (~14 keys, empty keybed), controls are text-only with no hardware widgets and no audio wiring, and the primary path is a placeholder synth.

  2. All section controls render as plain text labels with zero hardware widgets (no knobs/drawbars/faders/buttons/LEDs/OLEDs); no piano control (type/model/touch/compression/timbre/unison/volume/reverb/sustain) is rendered or wired to audio.

  4. Pointer/touch input is dead in the running app because inputHandler is undefined on the only render pass (App.tsx:138); only computer-keyboard input produces sound, and it uses fixed velocity 0.7 with no visual feedback and a wrong white-key pitch mapping.

Audio implementation

CriterionRatingScoreEvidence
Piano sound source 1/4 25
  • Primary path is a placeholder Tone.PolySynth(Tone.Synth) with a triangle oscillator and a generic ADSR (pianoEngine.ts:84-92) — a subtractive/basic synth, NOT sampled or convincingly piano-like.
  • IMPLEMENTATION_DETAILS.json labels it 'FM Synthesis via Tone.js PolySynth' with sampleSources:[] and recordedSamples:[]; the code is not even FM (it is a triangle Synth), and knownLimitations admits 'FM synthesis tone is stylized, not acoustic piano sample matching'.
  • This directly fails Phase 2 hard gate 1 ('primary piano path is not a placeholder oscillator or generated additive buffer bank') and piano spec acceptance 4 ('generated placeholder buffers do not satisfy this requirement').
  • Credit for 1 rather than 0: a real Tone.js audio graph exists and can make sound, so it is not literally silent/absent.
Note lifecycle and cleanup 2/4 50
  • NoteLifecycleService (noteLifecycle.ts) implements note-on/off keyed by sourceId, repeated-note replacement, and allNotesOff with per-source synthetic note-offs; unit-tested in audio-lifecycle.test.mjs.
  • PianoEngine.handleNoteOn/handleNoteOff/handleAllNotesOff (pianoEngine.ts:133-196) trigger Tone attack/release and release+reset voices; dispose() tears down nodes.
  • Weaknesses: note-off releases by frequency via synth.triggerRelease(frequency) but note-on ignores the allocated voiceId and calls triggerAttack directly, so voice tracking and the audio nodes are only loosely coupled; sustain branch uses setTimeout(500ms) rather than pedal-driven release (pianoEngine.ts:173-178).
  • All-notes-off in-app only reachable via Escape key; overall the lifecycle logic is coherent in isolation but its coupling to actual audio is thin and only exercisable via the keyboard path.
Velocity and sonic controls 1/4 25
  • Velocity math exists: pointerYToVelocity clamps 0.3-1 (Keyboard.tsx:112-119), touch force fallback, MIDI value/127; touch-curve pow() transform (pianoEngine.ts:264-277); these are unit-tested (audio-integration.test.mjs).
  • BUT in the running app there is no UI to change volume, reverb, or touch curve, so 'controls measurably change rendered audio' cannot be exercised by a user. setMasterVolume/setReverb are never called outside tests.
  • Keyboard-triggered notes use a fixed velocity of 0.7 (inputHandler.ts:191), so the only usable input path has no velocity variation; pointer velocity is unreachable due to the undefined inputHandler prop.
  • audio-real.test.mjs mostly checks typeof OfflineAudioContext and raw node .value assignments (e.g. osc.frequency.value===440) and does not validate PianoEngine output changing with controls.
Sustain and polyphony 1/4 25
  • VoiceManager (voiceManager.ts) implements 32-voice allocation and deterministic stealing (fifo/lru/velocity-weighted); unit-tested in audio-voice.test.mjs. Polyphony logic is solid in isolation.
  • However voices are allocated/stolen in the manager but the audio synth (Tone.PolySynth) is triggered independently by frequency and is not informed of stealing, so the manager's stealing does not actually cut audible voices — the two are decoupled (pianoEngine.ts:139-153).
  • Sustain is effectively non-functional audibly: input sets noteLifecycle.setSustain (inputHandler.ts:170), but PianoEngine.handleNoteOff reads this.config.sustain (pianoEngine.ts:171), which is only set via setSustain() that is never called from input. So the pedal does not extend note duration in the running app.
  • Fails Phase 2 hard gate 3 for sustain; polyphony exists as bookkeeping but not as an audible, engine-coupled behavior.

Playability and UX

CriterionRatingScoreEvidence
Playability 1/4 25
  • Live keybed is essentially unplayable by pointer: only ~8 white + ~6 black keys render (DOM: White key 0-7, Black key 0/1/3/4/5/7) instead of 73, because getKeyPattern returns a fixed 14-char string 'WBWBWWBWBWBWWB' and the loop iterates only those 14 chars (Keyboard.tsx:13-37).
  • Even those keys do not sound on click: inputHandler prop is undefined at render (App.tsx:138 with engineRef.current null; App never re-renders), so Keyboard.tsx:42 guard skips noteLifecycle.noteOn.
  • Computer keyboard DOES work: attachKeyboard binds window keydown/keyup to the engine lifecycle (App.tsx:47, inputHandler.ts:153-221), so pressing Q/W/E... can produce (placeholder-synth) sound after the click-to-resume gesture (App.tsx:68).
  • Pitch mapping is wrong: keyIndexToMidi uses [0,2,4,5,7,9,11] for consecutive white keys (Keyboard.tsx:105, inputHandler.ts:305), which is E F# G# A# B C# D#, not the correct E F G A B C D white-key scale.
  • Net: a knowledgeable user can coax notes only via QWERTY; the primary visual instrument (the keys) is broken.
Control feedback 1/4 25
  • Keys have pressed-state CSS (Keyboard.css:37-41,60-64) and pressedKeys state updates on pointer down/up (Keyboard.tsx:39-69), so the ~14 rendered keys do depress visually on click.
  • But QWERTY key presses (the only working audio input) provide NO visual feedback — the computer-keyboard handler never updates pressedKeys, so keys that actually sound do not light up.
  • No control widgets exist, so there is no knob rotation, LED toggling, or display illumination feedback for any parameter change.
  • Hover states exist for keys only.
Failure handling 2/4 50
  • MIDI: attachMIDI returns a no-op teardown when navigator.requestMIDIAccess is absent and catches permission/denied errors without throwing (inputHandler.ts:227-292); unit-tested in input-midi.test.mjs. This is graceful.
  • AudioContext fallback: AudioContextProvider.create() returns a non-running provider when window.AudioContext is missing and getContext throws a labeled 'AudioContext not available' error (audioContext.ts:26-49); audio-fallback.test.mjs covers this and PianoEngine staying constructible.
  • BUT the fallback is NOT surfaced to the user: there is no visible 'fallback'/degraded label in the UI (grep = none), and IMPLEMENTATION_DETAILS claims a 'visual-feedback-only' fallback that isn't rendered. Fails the labeled-fallback half of Phase 2 hard gate 4.
  • App.tsx swallows init errors to console.error only (App.tsx:73-75), so a user sees a blank instrument on failure with no indication.

Engineering quality

CriterionRatingScoreEvidence
Audio architecture 2/4 50
  • Reasonable separation of concerns in source: audioContext (injectable provider), noteLifecycle (event hub), voiceManager (allocation), pianoEngine (graph), inputHandler (routing), effectsGraph. Boundaries are testable with fakes/OfflineAudioContext, which is a plus.
  • Single audio graph in PianoEngine: Synth -> masterGain -> reverb -> compressor -> Tone.getDestination() (pianoEngine.ts:79-96). One destination.
  • BUT EffectsGraph (effectsGraph.ts) duplicates the same gain->reverb->compressor chain and is DEAD CODE — only re-exported from audio/index.ts, never instantiated (grep). Two parallel implementations of the master chain indicate architectural drift.
  • The voice manager is decoupled from the actual synth voices (bookkeeping only), and control setters are unreachable from the UI, so the 'architecture' is more scaffolding than a wired system.
Performance and cleanup 2/4 50
  • Cleanup is present: App unmount runs all input teardowns, allNotesOff, and pianoEngine.dispose() (App.tsx:81-102); dispose() disposes synth/gain/reverb/compressor and resets managers (pianoEngine.ts:236-253).
  • Keyboard listeners are removed on detach (inputHandler.ts:217-220); MIDI listeners removed on teardown.
  • Concerns: handleNoteOff schedules setTimeout for sustain without tracking/clearing timers, a minor leak risk under rapid play; voice steal deletes the manager entry but does not stop a corresponding audio voice, so under rapid polyphonic play the PolySynth manages its own voices while the manager count diverges.
  • No evidence of stress instability, but the divergence between bookkeeping and audio means claims of deterministic 32-voice stealing are not truly enforced on the audible graph.
