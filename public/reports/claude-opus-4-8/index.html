Phase 1

Complete surface and basic piano

Audio strategy
One basic piano voice produced by honest real-time synthesis in a single Web Audio AudioContext. Each note is a small additive oscillator stack (a triangle fundamental, a slightly detuned sine for body, and sine partials at the octave and twelfth) shaped by a per-note gain envelope. Velocity scales the peak gain on a squared curve; note-off applies a per-note linear release; sustain (UI/keyboard/MIDI CC64) holds released notes until the damper lifts. All voices route through one master gain into a DynamicsCompressor acting as a soft limiter, then to the single AudioContext.destination. Polyphony is bounded (16 voices) with deterministic oldest-first voice stealing. There are NO recorded samples in this phase.

Piano library and working effects

Audio strategy
One AudioContext (src/audio/audioEngine.ts). Two Piano layers (A, B) each own their voices and route only to their own layer bus. Each layer bus passes through an ordered effect chain — Mod 1 -> Mod 2 -> Delay -> Amp Sim/EQ (or Filter) -> Compressor -> Reverb — then a per-layer level gain into the master gain -> DynamicsCompressor limiter -> the single AudioContext.destination. Priority issues

  1. critical Every MIDI note is force-released one frame after note-on, and CC64 sustain with it: src/hooks/useMidiInput.ts:18 declares `provider: MidiAccessProvider | undefined = browserMidiProvider()` as a default parameter, so a new function identity is produced on every render of App. The effect's dependency array is [router, provider], so the effect tears down and re-subscribes on every render; its cleanup calls controller.disconnect() (which calls handlers.sustain(false)) and router.releaseOwner('midi'). Because a note-on itself re-renders App (activeNotes state), the note it just started is released one frame later. Measured on the published build: a MIDI note held 1500 ms is audible for ~300 ms (RMS 0.1749 at t=0.05 s, 0.0088 at t=0.30 s, 0 from t=0.35 s) and the voice counter never leaves 0; navigator.requestMIDIAccess was called 70 times in one short session. With CC64 held down, a note-off still silences the tone within 0.30 s. The unit test does not catch this because it injects a stable midiProvider prop, which is the one path that does not re-create the provider.
  2. major Sustain is not reachable by any input in the shipped build: There is no UI sustain control and no computer-keyboard sustain mapping (grep for sustain in src hits only midi.ts, useMidiInput.ts and three decorative SUSTPED button definitions; DEFAULT_KEYBOARD_MAP has no Space entry). Space with focus cleared does nothing - a note released while Space was held decayed normally 0.30 s after key-up. The only wired path, MIDI CC64, is nullified by the per-render MIDI teardown. Phase 1's hard gate lists sustain among the required piano behaviours, and the piano spec requires sustain from UI control, keyboard mapping and CC64.
  3. major The piano voice has no decay - it is a sustained organ-like tone with a slow beat: A held note stays at constant amplitude: RMS 0.1404 at t=0.10 s and 0.1417 at t=1.70 s of a 2.0 s hold. The only amplitude movement is a 0.61 Hz beat from the 4-cent detuned partial (dip to 0.0609 at t=0.85 s, back to 0.1417 at t=1.70 s, ~57% depth), which reads as a wobble rather than a piano decay. src/audio/pianoEngine.ts schedules attack and release only - no decay segment - and src/audio/webAudioBackend.ts holds the four oscillators at fixed gain for the whole note.
  4. major No velocity response from pointer or computer keyboard, and clipping under polyphonic load: Keybed.tsx:26 and useKeyboardInput.ts:39 both pass a constant velocity of 100, so a click at 12% of key height and one at 92% produce bit-identical peaks (0.14161); velocity only varies over MIDI (0.00451 at v20 vs 0.17706 at v110), which is itself broken. Separately, 20 keyboard notes held together reach a peak sample amplitude of 1.528 against full scale 1.0 (RMS 0.486) at the node feeding AudioContext.destination, so the master gain 0.6 into DynamicsCompressor(threshold -6, ratio 12) does not prevent hard clipping.
  5. minor The voice counter reports held keys, not sounding voices: The engine caps polyphony at 16 with oldest-first stealing (src/audio/pianoEngine.ts:43,95,163), but the status bar counts NoteRouter's held pitches. Holding 20 mapped keys displays "20 voices" while at most 16 tones can exist. Small, but it is a status line whose whole purpose is truthfulness.
  6. minor Program section clips its own OLED and eighth program button: The program section's content overflows its box by 53.7 px with overflow:hidden, so the primary OLED renders "A:11 / Nord Sta" cut mid-word and the eighth program button's legend is sliced. Root cause is the section-width table in src/model/controls.ts (performance 0.13, organ 0.21, piano 0.15, program 0.09, synth 0.21, effects 0.21) against the spec's 0.14 / 0.20 / 0.085 / 0.125 / 0.25 / 0.20; measured rendered fractions are 0.128 / 0.207 / 0.148 / 0.089 / 0.207 / 0.207, worst deviation 0.063. Every control remains pointer-reachable, so this is legibility rather than loss of inventory.
  7. minor MIDI device disconnect does not release that device's sounding notes: src/input/midi.ts:84-90 handles a port statechange of 'disconnected' by calling handlers.sustain(false) and setState('disconnected') only; it never releases notes the device owns.
