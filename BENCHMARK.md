# Stagebench — Nord Stage 4 recreation benchmark (protocol 3.0)

Stagebench measures how well a coding-agent configuration can recreate the Nord Stage 4 as an interactive browser instrument, working incrementally from a product photo, the user manual, and machine-readable specs. It exercises dense reference-driven UI, accessibility, browser input, real-time audio, state architecture, and regression-safe extension of an existing artifact.

This file documents the protocol and harness for operators and evaluators. The candidate-facing task — phases, honesty contract, implementation requirements, and required feature IDs — lives in [TASK.md](./TASK.md), which is what run workspaces receive (filtered to the phases the run has reached). Candidates never see this file, the rubric, other runs, or the harness.

**Protocol 3.0** is the current protocol: candidates run offline inside the [lockdown](./docs/LOCKDOWN.md), are not told which model or run they are, work under a fixed budget with at most two seal-failure rounds per phase, build from one shared sample pack, and are graded blind by a boxed evaluator; tokens and cost come from the gateway's log. **Rubric 3.0.0** scores sound from measurements the harness takes at seal and makes every sound criterion reachable from the pack. What changed from 2.0, and why, is in [docs/PROTOCOL-3.md](./docs/PROTOCOL-3.md). Runs created under rubric 2.0.0 keep it (`bench/rubrics/2.0.0.json`).

## Source-of-truth files

- `TASK.md` — the candidate-facing task definition and required feature IDs.
- `specs/benchmark-phases.json` — phase scopes, hard gates, and shared completion gates.
- `specs/nord-stage-4.visual.json` + `specs/nord-stage-4.variants.json` — surface geometry and the three hardware variants.
- `specs/nord-stage-4.piano.json`, `…effects.json`, `…organ.json`, `…synth.json`, `…programs.json` — per-section behavior, summarized from the manual with page citations.
- `prompts/stage1.md` … `stage3.md` — the per-phase instructions given to the implementation agent.
- `bench/rubric.json` — the current rubric (3.0.0): scoring weights, the pinned evaluator model id, the computed-criterion measurement specs, and the harness-measured audio criteria. Earlier rubrics a run can still be scored by are frozen in `bench/rubrics/<version>.json`; a run is scored by the one current when it was created. Never given to candidates.
- `bench/prices.json` — the pinned, dated API price table that turns gateway-logged tokens into cost (USD per million tokens, with its sources and read date).
- `sample-pack/manifest.json` — the one sample pack: every recording a candidate may bundle, pinned to an upstream commit and a sha256, with its license. The audio is fetched, not committed.
- `bench/lockdown/image/npm-mirror.lock.json` — every package a candidate can install, pinned by sha512. It defines the offline mirror baked into the candidate image.

**What counts as the artifact.** The sealed artifact is the candidate's *source*: `dist/` is excluded from it and from the digest, because the build is derived from source by a documented command and the built app is already committed per phase under `public/previews/`. This is not a preference — `.gitignore` matches `dist` at any depth, so a digest that covered `dist` could never validate in a fresh checkout, and 42 of 42 sealed digests didn't. `pnpm bench redigest` re-records digests when the definition changes and stamps `artifactDigestVersion`, so a stale digest stays an auditable fact rather than a check everyone learns to skip.

## Honesty contract

The core rule in every phase (stated in full in `TASK.md`): a control either works canonically or it visibly exists, moves, and does nothing — it never fakes success, and evidence never claims unimplemented behavior. Verification and evaluation both check this boundary, and `IMPLEMENTATION_DETAILS.json` must truthfully declare every audio source.

## Running the benchmark

Once per machine, set up the lockdown and fetch what is not in the repository: the copyrighted reference assets (never redistributed here) and the sample pack (each file from its pinned upstream commit, checked against its sha256; WAV recordings are stored as FLAC-coded samples, which needs the `flac` command, and rebuilt byte for byte when a phase starts):

```sh
pnpm bench lockdown-setup     # container VM with no host directories, both images, self-tests
pnpm bench fetch              # manual, photos, sample pack
pnpm bench redteam            # attack the boundary from inside; expect every attempt blocked
```

Then a run is:

```sh
pnpm bench new --model <id> --target <1|2|3> [--variant stage-4-73]
pnpm bench start <run-id>     # per phase: creates the implementation workspace
pnpm bench agent <run-id> --harness <codex|claude|custom>   # per phase: runs the implementation agent inside the lockdown, offline
pnpm bench seal <run-id>      # per phase: export + gates + capture + sample check + verify + transcripts + seal
pnpm bench score <run-id>     # per phase: builds the blind evaluator workspace
pnpm bench evaluator <run-id> --harness claude              # per phase: runs the evaluator inside a lockdown box
pnpm bench score <run-id>     # per phase: registers the filled assessment
```

If a seal fails, the candidate is told with the seal's own words and nothing else: `pnpm bench agent <run-id> --harness <same> --message seal-failure`.

After the selected phases are sealed and scored, and before committing or publishing the run, generate the gallery hover thumbnail from the published preview:

```sh
pnpm bench thumbs <run-id>
```

`thumbs` screenshots the published build at `public/previews/<run-id>/stage<N>/` (the stage named by `previewPath`) and writes `thumb.jpg` next to `index.html`. The gallery addresses that image by swapping `index.html` for `thumb.jpg` on `previewPath`, so the run record gains no new field. A published preview without `thumb.jpg` still plays; its leaderboard row simply has no hover card. The command does not re-seal or re-score.

**Workspaces live outside the repo.** All transient workspaces (implementation, evaluation, gate scratch) are created under `~/.stagebench/<repo-key>/` — never inside the repository tree — so a candidate or evaluator agent cannot reach `runs/`, `showcase/`, or other solutions with a relative `../..`. Override the base with `STAGEBENCH_HOME`. `pnpm bench clean <run-id>` (or `--all`) removes them; `bench status` surfaces any that linger.

**Implementation isolation.** `start` builds `<home>/work/<id>/stage<N>/` containing `candidate/` (the starter, or the preceding sealed artifact) and `inputs/` with exactly the phase's materials: the phase prompt, the assigned specs, `TASK.md` and `specs/benchmark-phases.json` filtered to phases ≤ the current one, only the assigned variant's entry (also pinned as `defaultVariant`), the implementation-details schema, the manual, and the variant photo. Protocol 3 adds four things, so that a candidate never has a reason to look anywhere else: the capture harness the prompts refer to (`inputs/harness/`, with a one-command wrapper that writes the canonical captures into `candidate/evidence/`), the phase's hard gates as a block to paste (`inputs/hard-gates.md`), the sample pack (`inputs/samples/`), and the list of what can be installed offline (`inputs/OFFLINE.md`). `WORKSPACE.md` does not name the run, tells the candidate not to look outside the workspace, not to read the parent repository, other runs, other projects, scoring materials, or the harness, not to reuse sample banks from other projects, and not to name itself. The implementation agent never sees `runs/`, other solutions, future phase details, scoring materials, or the harness.

**Lockdown.** Workspaces being out of the repository tree stops a relative `../..`; it does not stop an absolute path, a network fetch, or a tool that runs outside the agent's own sandbox, and those are how earlier candidates came to read the rubric and copy sample banks. New runs therefore require the lockdown (`pnpm bench new` records `isolation: lockdown`). `pnpm bench agent <run-id> --harness <name>` copies the workspace into container volumes and runs the harness there: none of this machine's filesystem is mounted, in the container or in the VM under it, and every tool the harness starts — shell, MCP servers, REPLs, nested agents — runs inside the same box. The candidate has no internet. Its only egress is its own model API, through a gateway that allows exact endpoints and removes hosted tools such as web search. Packages install from a fixed, hashed mirror baked into the image and served on loopback; the browser is in the image; recordings are the sample pack. `seal` exports the candidate from its volume, drops any symlink, refuses an artifact that contains the session credential, runs the gates, the canonical capture, and the sample check inside boxes with no network, and writes what the boundary observed into the verification record (`isolation`) and `runs/<id>/lockdown/`. `pnpm bench exec <run-id> --command "..."` runs a command in the same box, with no network. Design, threat model, and limits: [docs/LOCKDOWN.md](./docs/LOCKDOWN.md); red-team results: [docs/LOCKDOWN-REDTEAM.md](./docs/LOCKDOWN-REDTEAM.md).

**Outside the lockdown.** `--isolation none` at `new`, or `seal --unlocked`, is possible and never silent: the stage records `isolation: none`, and the gallery footnotes the run as not an official protocol 3 result. If the agent is Codex, launch it with `scripts/bench-candidate-codex -C <workspace>` so the session uses the `candidate-isolated` permission profile in `bench/codex-candidate.config.toml` (workspace writes, no reads of the rest of the disk, no MCP servers, no network). Do not pass `--sandbox` or `--dangerously-bypass-approvals-and-sandbox`; those flags fall back to the legacy sandbox, which allows reading the whole disk. Confirm the profile with `scripts/verify-candidate-sandbox.sh`. This is one harness's own sandbox, and a fallback: it is not the lockdown.

**Operator messages.** An operator does not compose messages to a boxed agent. The first message of a phase is fixed. After that there are two templates: `--message continue` (the session ended early) and `--message seal-failure` (relays the failed seal's own output, taken from the harness's record of it, with host paths and the run's name removed). Each launch is recorded with its template and text. A message outside the templates has to be sent as `--off-protocol-message "…"`, which marks the phase and footnotes the run.

**Sealing.** `seal` imports the candidate, reruns the four package gates, captures parent-controlled 1440x900 and 390x844 screenshots of the built artifact (in the image's own Chromium, for a locked phase), verifies the phase contract/feature matrix/evidence/provenance, hashes the tree into `runs/<id>/verifications/stage<N>.json`, and publishes the preview. The sealed `runs/<id>/stage<N>/` tree keeps only source, `dist/`, and evidence — never an installed `node_modules` (gates run against a copy). The candidate also writes `evidence/stage<N>-visual-audit.md` describing measurements, exercised flows, and known deviations.

Under protocol 3 a seal also fails when: a feature in `tests/feature-matrix.json` maps only to tests that the seal's own test run did not execute or that skipped every test (a suite behind `runIf`, a standalone browser script); a bundled audio file is undeclared, or does not acoustically match the pack recording it is declared to come from; the artifact names the model or run that produced it; or there is no agent transcript to archive. Each failure is a message a candidate can act on. The full list and the reasoning are in [docs/PROTOCOL-3.md](./docs/PROTOCOL-3.md).

**Sealed evidence is never edited.** Every seal appends the artifact digest to `runs/<id>/ledger.jsonl` (hash-chained). A phase the ledger holds cannot be sealed again; `redigest` moves a digest only when the artifact definition itself changed; `pnpm bench verify-sealed` re-hashes every sealed stage against `run.json` and the ledger; `score` refuses a stage that no longer matches. An operator who changes an artifact after sealing does it as a new run: `pnpm bench fork <run-id> --to <new-id> --reason "..."` copies the earlier phases as sealed, reopens the rest from the source's sealed artifacts, records which files the patch changed, and labels the result as an operator patch everywhere. The original keeps its score.

**Transcripts.** After the digest is recorded, `seal` archives the agent sessions that produced the phase into `runs/<id>/transcripts/phase-<N>/` — Codex rollouts, Claude Code project sessions (with subagents and offloaded tool output), and Cursor agent transcripts whose working directory is the phase workspace or its `candidate/` — secret-scrubbed (`bench/lib/scrub.mjs`) and zstd-compressed, with a `manifest.json` (sizes, sha256 of the scrubbed bytes, redaction counts) and a derived `operator.jsonl` of the operator's messages, interrupts, approvals, and permission changes. The harness also appends `start`/`seal`/`score` events to `runs/<id>/transcripts/operator.jsonl`. Pass `--transcripts <file[,file...]>` for sessions stored elsewhere, or archive later with `pnpm bench transcripts <id> --phase <N>`. Transcripts are sidecar records outside `stage<N>/`, so they are never part of the artifact or its digest. Under protocol 3 a phase is not sealed without its transcript: a locked phase's session files and the launcher's console logs come out of the box with the candidate tree, and a phase sealed outside the lockdown needs a discovered or named session. (Before protocol 3 a missing transcript printed a warning and recorded the gap; 22 of the 27 earlier runs cannot be audited for that reason.) The second `score` call archives the evaluator/reviewer sessions into `transcripts/eval/phase-<N>/` the same way. Layout, reading, and historical coverage: [`runs/TRANSCRIPTS.md`](runs/TRANSCRIPTS.md).

**Telemetry.** Wall time per phase is recorded automatically (start → seal). For a boxed (protocol 3) phase, tokens and cost come from the lockdown gateway's own hash-chained log: every model response's usage (input, cached input, cache writes, output, reasoning where the provider reports it), the model id the provider says served it, and its request id, priced with the pinned table in `bench/prices.json`. Those are the official figures. Figures typed at seal or afterwards (`--cost-usd`, `--input-tokens`, … on `seal` or `pnpm bench telemetry <id> --phase <N>`) are recorded as **operator-entered and non-official**: for a boxed phase they are kept beside the gateway's (`operatorTelemetry`) and never replace them; for a phase with no gateway (protocol 2 and earlier, `--isolation none`) they are all there is and are labelled as typed. Per-phase values roll up by summing the phases that recorded each field; unrecorded values stay `null`, never zero. `totalTokens` is input plus output. Reasoning tokens are a separate count and are not included in that total.

The gallery currently hides token counts (no Tokens column, no token rows in run details) because coverage and definitions are inconsistent across harnesses; the data below is still recorded in `run.json` and `src/data/runs.json`. When shown, the Tokens column is full-run usage only. It shows a recorded `totalTokens` when every phase has one, or when the run stores a single total with no phase split. When every phase recorded input and output but not a total, the column uses that same in-plus-out definition. A sum of only some phases is not shown as the run total: the column reads "partial", and the run details name the phases that were recorded. Missing phase splits are left blank — they are not inferred from a run-level total.

> **Gotcha — don't hand-enter `subagent_tokens`.** The Claude Code run-completion notification reports a `subagent_tokens` figure that is the subagent's *final context size*, not the tokens it generated. Entering it as `--output-tokens` overstates usage (observed ~2.1× on one run). The honest number is the sum of per-turn `output_tokens` across the subagent transcript. Recompute it from the JSONL transcript(s) instead of copying the notification: `pnpm bench telemetry <id> --phase <N> --from-jsonl <transcript.jsonl>`, or preview the numbers first with `pnpm telemetry:from-jsonl <transcript.jsonl>` (which prints the ready-to-paste flags). Reasoning tokens aren't in the transcript — Claude bills thinking as output — so add `--reasoning-tokens` by hand only if you have a separate figure.

`bench status <run-id>` always prints the next command plus recorded telemetry. `pnpm bench help` lists everything.

## Evaluation

Evaluation is a separate, isolated flow from the run. The first `bench score` call builds `<home>/eval/<blind-handle>/stage<N>/` containing `artifact/` (a copy of the sealed phase, chmod'd read-only, its digest re-checked against the seal so the evaluator provably rates the sealed bits), `build/` (the published build of that phase, so every evaluator measures identical bits rather than each building its own), `inputs/` (the rubric, `TASK.md`, phase contracts, assigned specs, variant entry, manual, photo, and the sealed verification record), the `assessment.json` template, and `EVAL.md` instructions. The directory is named by a **blind handle**, not the run id, and the template carries that handle — the evaluator is not told which model produced the artifact. A **fresh evaluator agent** — independent of the implementation agent, working only inside that directory — inspects the artifact against the rubric and fills the assessment in, each entry with concrete evidence. It never reads `runs/`, other runs' scores, or any other solution.

**Blind all the way down.** The handle is keyed with a secret in the operator's Stagebench home, so it cannot be worked back to a run id. The workspace path has no checkout name in it (`<home>/eval/<hash>/<handle>/stage<N>`). The grader's copy of the artifact has its agent instruction files removed (`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.cursor/`, … — a harness loads those on its own, so in an artifact they are addressed to the grader) and the producer's name redacted wherever the artifact wrote it; the sealed tree is not touched. The grader's copy of the seal record has no isolation record, no operator messages, and no host paths.

**The evaluator runs in a box.** For a run that requires the lockdown, `pnpm bench evaluator <run-id> [--phase N] --harness claude` runs the grader in a container whose only contents are that workspace — artifact, build, and inputs read-only; the assessment and a scratch directory writable — with its own model API as its only network. The model is the one the rubric pins. `--slot 2`, `--slot 3` add independent panel members, each in its own box and each starting from the blank template; `--message review` runs a fresh independent reviewer over a filled assessment. The assessment is copied back for the registering `score` call, and the grader's transcripts and its gateway's record are archived with the run.

**The evaluator model is pinned** in `bench/rubric.json` under `evaluator.model`, and registration rejects an assessment produced by anything else. Scores from different judges are not comparable, and the field that used to record the judge was free text that said "opus-4.8", "evaluator-1", or nothing at all. Because the candidate may be built on a harness that cannot run the pinned model, evaluation is invoked separately — see the `eval-nord-benchmark` skill.

**Three kinds of criterion.** A *judged* criterion takes a 0–4 rating against the rubric anchors. A *computed* criterion takes no rating at all: the evaluator reports measurements and the score is derived, so no judgment enters where the specs already give ground truth. Seventy percent of the panel axis is computed — geometry, hardware inventory, keybed layout and colour fidelity all reduce to numbers the specs already fix. A *harness* criterion (rubric 3.0.0) is not the evaluator's at all: at seal the harness plays a fixed list of test notes into the build over Web MIDI, records what it renders, and measures tuning, velocity response, releases, clicks, sustain, latency, polyphony, and clipping; the score is derived from that record (`evidence/stage<N>-audio.json`), and a measurement the build gave nothing to measure scores zero. The test plan and thresholds are in [docs/PROTOCOL-3.md](./docs/PROTOCOL-3.md#9-harness-measured-audio-rubric-300).

**The grader's model id is recorded.** For a boxed evaluation the gateway logs, for every request, the model id it asked for, the id the provider says served it, and the provider's request id. Registration writes them to the ledger (`grader`), keeps the full request-id list in `runs/<id>/lockdown/stage<N>.evaluators.json`, and flags drift if a request for the pinned model came back as any other id.

Running `bench score` again validates the assessment, confirms the sealed digest is unchanged, reruns the technical checks **against an out-of-repo copy** (the sealed tree is never mutated; for a run that requires the lockdown, or with `--sandbox` / `STAGEBENCH_SANDBOX=1`, they run inside the lockdown box so candidate code never executes on this machine — with no network for a protocol-3 artifact, and with a read-only package mirror for one sealed earlier, whose lockfile names packages the offline mirror does not carry), maps the blind handle back to the run, computes the score, archives the assessment into `runs/<id>/evaluations/`, writes the gallery report, and removes the evaluator workspace. A failed technical check caps the phase at 59, a missing build at 49.

**The aggregate is the run-level panel axis plus the phase-weighted remainder.** Panel fidelity is worth 40% and is scored **once**, against the highest sealed phase — the phases are cumulative, so rating the same panel three times measured it at three different resolutions, and a regression introduced late is caught anyway because the final artifact is the regressed one. The other 60% is the three phase scores at 25/30/45. Panel fidelity also carries **hard gates keyed on individual measurements** rather than on the criterion score: a keybed with the right key count, the right split and the right height ratio whose keys simply do not lay out inside it averages to a passing number, which is exactly the failure the gate exists to catch.

**Evaluator panels.** For a phase, additional independent evaluators may fill `assessment.2.json`, `assessment.3.json`, … beside the primary `assessment.json`. Registration takes the per-criterion **median** across the panel before scoring — the median rating for judged criteria, and the median of each reported value for computed ones, so a panel damps measurement-method spread the same way it damps judgment spread — unioning the evidence with attribution. This cuts single-observation noise. A lone evaluator is the common case and passes through unchanged.

**Gate environment.** The isolated gate reproduces the platform types the in-repo environment provided by directory walk-up (the starter never declared `@types/node`, so candidate typechecks resolve it ambiently); the copy is given the same `@types/node` after install. This keeps out-of-repo scoring identical to how every prior run was evaluated, rather than silently failing a candidate that relied on the ambient toolchain.

## Interpreting results

- The unit under test is the full agent configuration recorded in `run.json` — not a base model in the abstract.
- A single run is one stochastic observation; small score differences are within evaluator noise. The evaluator works from a blind handle rather than the run id, but blinding is best-effort — an artifact's own source may still reveal its author, and evaluations are not blinded to the task itself. Use a panel to reduce noise further.
- The Nord Stage 4 is a public product; training-data familiarity cannot be ruled out. Results mean "performance on this disclosed task".
- Prompts, specs, rubric, and verifier behavior are comparison-critical: changing them means bumping the protocol version, and runs from different protocol versions are not comparable. Protocol 1.1 changed the materials packaging (candidates no longer see scoring/harness docs, future phase details, or unassigned variants; evaluators work in an isolated workspace) — task content is unchanged from 1.0. Protocol 2.0 rewrote the rubric: four constant axes per phase, panel fidelity promoted to a run-level axis scored once at 40%, computed criteria replacing ratings wherever the specs give ground truth, a pinned evaluator model, and constrained evidence and issue shapes. Task content is again unchanged — 2.0 changes how a run is scored, not what is asked of it. Protocol 3.0 does not change what is asked. It changes the conditions — candidates are offline in the lockdown, are not told who they are, work under a fixed budget and a fixed number of seal-failure rounds, build from one shared sample pack, are held to executed feature tests and declared sample provenance, and are graded blind in a box (see [docs/PROTOCOL-3.md](./docs/PROTOCOL-3.md)). Rubric 3.0.0 changes how sound is scored (measured by the harness, reachable from the pack). A run is scored by the rubric current when it was created: every run made before rubric 3.0.0 keeps 2.0.0, and the gallery ranks each rubric on its own board, showing each run's protocol version, isolation mode, and footnotes. Runs recorded before the current run schema are shown as **Legacy** in the gallery with their frozen scores and reports.

## Run records

`runs/<id>/run.json` is the only authoritative run record; `src/data/runs.json` is a generated projection (`pnpm bench reindex`, run automatically before dev/build). Beside it: `ledger.jsonl` (what was sealed and scored, append-only), `lockdown/` (what the boundary observed for each phase and each evaluation), `transcripts/`, and, for an operator-patched fork, `patches/`. Footnotes shown in the gallery are derived from the record (a phase sealed outside the lockdown, an off-protocol operator message, an operator patch) or attached with `pnpm bench footnote <run-id> --add "..."`. Sealed phases record artifact digests; scored phases record evaluations and static HTML reports under `public/reports/<id>/`. Gallery hover thumbnails are `public/previews/<id>/stage<N>/thumb.jpg`, produced by `pnpm bench thumbs <id>` after the preview is published.
