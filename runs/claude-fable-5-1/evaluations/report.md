### Phase 1: Complete surface and basic piano

- Audio strategy: Generated buffers only. One piano-like voice is synthesized at runtime by additive synthesis (src/audio/pianoRenderer.ts) into Float32 AudioBuffers per note and velocity layer, played through AudioBufferSourceNode -> per-voice GainNode -> master GainNode -> destination. No recorded samples are bundled or fetched. Nothing is described as a recording.
- Generated sound sources: Generated additive piano voice — Up to 28 inharmonic partials (f_n = n·f0·sqrt(1+B·n²)) with a hammer-position comb filter, velocity-dependent brightness (partial roll-off exponent), two-stage exponential decay (prompt sound + aftersound), a 2 ms attack ramp and a 9 ms seeded-noise hammer thump. Peak-normalized then scaled by the velocity loudness curve. Deterministic for identical inputs.; Fallback triangle tone — Only used when the piano renderer throws. A triangle OscillatorNode with a 5 ms attack and 2.5 s exponential decay through the same per-voice gain and master path. The status strip and program display label this state as 'fallback'.
- Recorded sample provenance: No recorded or external sample sources declared
- Bundled audio: None detected
- Audio note: Web Audio is created lazily on the first key press or the Start audio button; status is reported as idle, loading (warm-up bank rendering), ready, error (no AudioContext available) or fallback (renderer failure).
- Audio note: Sustain (UI pedal button, Shift key, MIDI CC64) is the only panel-independent audio behaviour; every physical panel control is decorative in Phase 1 and changes presentation state only.
- Audio note: Polyphony is capped at 32 voices; the oldest sounding voice is stolen deterministically with a 20 ms release. Note release is a 300 ms exponential ramp; retriggered notes release in 30 ms; all-notes-off uses 80 ms.
- Audio note: Tests never touch real audio output, MIDI devices or the network: the audio context, MIDI access and timers are injected (src/audio/boundaries.ts) and faked in tests (src/audio/fakeAudio.ts); audible relationships are proved on rendered sample data through src/audio/offlineRender.ts.

### Priority issues

- **major** — Simultaneous chords clip the master output: There is no headroom or limiter on the master path: engine master gain is fixed at 0.800 and each voice is peak-normalised to about 0.72 x the velocity curve, so in-phase attacks sum past full scale. Measured at the master node of the served build after a warm-up pass: a simultaneous 7-note fff chord (MIDI 48/52/55/60/64/67/72 at v127) peaks at 2.464 with 4392 sampled values at or above 1.0, which the destination hard-clips. A single note peaks at 0.484 and a staggered pedalled arpeggio of the same notes at 0.947, so the defect is specific to simultaneous onsets - exactly the way a piano is played. Re-measured across separate runs and reproducible. Re-confirmed on a second independent tap of the master GainNode via a ScriptProcessor sink (scratch/rv8-clip.mjs): the same 7-note chord peaked at 1.762 with 606 of 49,152 sampled values at or above full scale, against 0.576 for a single v127 note and 0.000 in silence; the exact peak varies with where the capture window falls across the onset, the clipping does not.
- **minor** — Pointer and touch cannot play below velocity 48: Keybed velocity is derived from the strike position as round(48 + 79 * fraction), so the softest note reachable with a mouse or a finger is v48 (measured lastNote '60@56' at the top of the key, '60@123' at the bottom). MIDI and the internal note bus reach the full 1..127, and the computer keyboard sends a fixed v96, so the restriction only affects on-screen play; it still costs about a third of the available dynamic range for the instrument's primary input.
- **minor** — Program OLED reports a voice while audio is in the error state: With window.AudioContext removed, the engine correctly reports state 'error' with the message 'Audio unavailable: Web Audio is not available in this browser. Keys still show presses; nothing sounds.', and the OLED's own next line reads 'Audio error'. But the line above it still reads 'Voice: generated tone', naming a voice that cannot sound. The status strip is fully honest; only this one OLED line is stale in the error state.

## Phase 2: Piano library and working effects

**71/100**

Phase 2 is largely built and honestly documented, and one defect undermines its centre. All six piano types are real, separately sourced recorded sets (8 sets, 471 ogg files, 14 MB), audibly distinct - centroids 601-2217 Hz, decay-to-25% 709-1452 ms, pairwise cosine distance up to 0.32 - with complete redistributable provenance. Two layers, focus, level, octave, velocity from pointer/keyboard/MIDI, sustain and CC64, the labelled asset-failure fallback, one AudioContext, per-layer buses and a master limiter holding a 12-note cluster at peak 0.948 without clipping all work as specified. Every effect unit and type is present and pointer-reachable (38/38 pass a 5x5 elementFromPoint test), and the DSP is real: set before audio starts, reverb types, amp models, delay, tremolo and rotary are plainly audible. But once the AudioContext exists the app posts partial parameter patches to a worklet that replaces its whole parameter set, so the message throws silently and no effect on/off, type, dry/wet or bypass - and no String Res - ever changes rendered audio again. The effects panel is presentation-only in the shipped build, undisclosed.

### Priority issues

- **critical** — No effect parameter, type or bypass reaches the audio once the AudioContext exists: After the first full parameter push, InstrumentController/EffectsEngine send only a diff patch (artifact/src/audio/engine.ts:601, instrumentController.ts:490-500) while the worklet's LayerChain.setParams replaces the whole ChainParams and reads p.timbre.family first (artifact/src/dsp/chain.ts), so every patch throws inside the AudioWorklet and is discarded. Measured in the served build: Mod 1 Tremolo amount 10 on/off gives identical envelopes (rms 0.02706 vs 0.02713); Delay ON with feedback 10 and dry/wet 8.3 adds no repeats (0.03375 vs 0.03405); Reverb ON at dry/wet 10 changes nothing (0.03478 vs 0.03405); 25 live unit/type/bypass changes all land within cosine distance 0.0005 of the baseline. The same settings applied before audio starts are plainly audible, so the DSP is correct and only unreachable. This defeats the Phase 2 hard gates on measurable change, per-unit bypass and dry/wet.
- **critical** — String Res never produces sympathetic resonance: The per-note held-string update is sent as setChain(id, {stringRes}) (artifact/src/audio/engine.ts:936), a patch with no timbre key, so it hits the same worklet defect and the resonator is never told which strings are undamped. Acoustics = String resonance vs Off, both set before audio start, render a three-note chord identically (rms 0.04805 vs 0.04802, peak 0.5776 both, log-spectrum cosine distance 0.0000). String Res is a required Phase 2 control.
- **major** — IMPLEMENTATION_DETAILS and the visual audit claim effect controls that do not work: controls.functional lists every effect unit and piano.acoustics as functional and audio.strategy describes the live chain, with no declared gap. evidence/stage2-visual-audit.md's DSP proof runs the worklet in a fresh OfflineAudioContext (the one path that gets a complete parameter object) and its panel pass verifies only canonical state, so neither document is contradicted by its own evidence while the shipped build is.
- **major** — The test double diverges from the real worklet, so the suite cannot see the defect: artifact/src/audio/fakeAudio.ts:115 merges parameter patches (mergeParams) while the production worklet replaces them, and the parameter message throws silently inside the AudioWorkletGlobalScope with no console error and no onprocessorerror. tests/effects.processing and tests/effects.routing therefore pass against behaviour the built app does not have, and nothing in the running build reports the failure.
- **minor** — All sample sets are mono: build/samples/*/manifest.json declares channels: 1 for all eight sets at 44.1 kHz with 3-semitone root spacing and 3-4 velocity layers, so the recorded pianos have no stereo image before the effects; a knowledgeable player would notice this against the hardware.
