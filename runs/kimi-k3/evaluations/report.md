### Priority issues

- **major** — MIDI disconnect does not stop owned voices, though the artifact claims it does: With a note held from an injected MIDI device, firing the device statechange leaves the voice untouched: RMS 0.0483 after the disconnect versus 0.0488 in an identically timed control run without one. Impact is bounded because voices are finite 8 s buffers that ring out on their own, so no note is permanently stuck; the defect is the false claim plus the missing allNotesOff on statechange in artifact/src/App.tsx.
- **major** — Destination clipping on loud chords: Measured peak at the destination tap is 1.21 for a 10-note velocity-127 chord and 1.55 for 16 notes, both beyond the [-1,1] clamp, so a fortissimo chord distorts. ## Phase 2: Piano library and working effects

**56/100**

Measured against build/ (bundle assets/index-Dj4VwXwL.js confirmed) with a destination tap patched onto AudioNode.connect plus a per-voice AudioBuffer tap. The DSP is genuinely strong: six audibly distinct piano types, Grand/Upright/Electric backed by 36 real WAVs each (18 roots x pp/ff, 22.05 kHz/16-bit), and Mod 1 (6/6), Mod 2 (6/6), Delay (in-loop LP/HP/BP), Amp/EQ (Twin/JC/Small/LP24/HP24), Compressor and Reverb (Booth 0.0015 -> Cathedral 0.0134 tail energy) each change rendered signal and differ from their siblings; per-unit and master bypass are bit-identical to baseline. ### Priority issues

- **critical** — Rotary is disconnected from the audio path while the panel reports it engaged: With amp type To Rotary, ROTARY on and speed FAST, the destination capture is unchanged from rotary-off (rms 0.04156 vs 0.04153, peak 0.2507 vs 0.2501, rmsL identical to rmsR to full precision - a horn/rotor would pan hard at 6.8 Hz). The per-voice buffer with To Rotary is bit-identical to EQ only, and the AudioNode.connect census contains no rotary DSP node; web-audio-backend.ts withoutLiveUnits() rewrites amp type 6 to 0 and sets rotary.on = false, and the rotaryInput GainNode it creates is never fed. The panel LED, the visual audit and IMPLEMENTATION_DETAILS all report a working Rotary. This is the honesty-contract failure the phase gates on: a claimed audio feature not connected to the audible signal graph.
- **critical** — Two piano layers never stack, and a layer button can leave the instrument silent: Both layer buttons lit still produces exactly one voice per key press (engine.noteOn routes only to focusedLayer), so the Phase 2 outcome 'two piano layers' is unreachable - measured as 1 AudioBufferSourceNode start and the focused layer's fingerprint. Worse, pressing a lit layer button disables that layer AND moves focus to it (syncFunctionalControls corrects focus, then pressFunctionalControl overrides it), so the keybed goes completely silent with the other layer enabled and lit: 0 voices measured after pressing B (A still on) and again after pressing A (B still on). Recovery only happens when some other functional control is touched.
- **major** — String Res is inert in the built app: The rendered voice buffer is bit-identical with String Res on and off (identical fingerprint, 0.00 dB rms delta), and a two-note held comparison differs by less than the measured capture noise. render.ts adds sympathetic resonance only when one render contains two or more held voices, but the Web Audio backend renders each voice in its own single-note render, so the control - declared functional and asserted by the offline tests - can never change what the user hears.
- **major** — Declared coverage describes the offline renderer, not the shipped backend: Five feature-matrix/IMPLEMENTATION_DETAILS claims are contradicted by measurement of build/: Rotary live in the browser, 'two types sound together', String Res sympathetic energy, 'limiter bound peaks <= 1.0' (measured 1.068 and 1.290 at the destination), and reverb 'fully wet at max' (dry onset unchanged at max). All five hold in the deterministic offline renderGraph the unit tests exercise; the WebAudioBackend diverges from it (per-voice baking, reverb replaced by a parallel send, rotary dropped) and nothing in the declaration records that divergence.
- **major** — Sample-load failure triggers an unbounded fetch retry storm: Aborting requests to ./samples/** yields the correct labeled fallback and a playable voice, but markTypeFailed -> pushConfig -> configure -> ensureLibrary re-issues the failed load on every state push with no failure memo: the page logged 182,120 console errors and unhandled 'Failed to fetch' rejections in roughly 15 s. The degradation is visible but it also floods the console and the network indefinitely.
- **major** — Per-note synchronous rendering blocks the main thread, and loud amp types push the bus over full scale: Each new note+config combination renders 8 s of audio through the whole chain on the main thread: 51-97 ms per note, 268 ms for a 5- or 10-note chord, 573 ms for a 10-note chord with the amp engaged, 499 ms to dispatch 22 key-downs. Separately, amp types raise the bus level by +15.0 dB (Twin) and +17.8 dB (Small) before the DynamicsCompressor limiter, and the destination peaks at 1.068 (10 notes, no amp) and 1.290 (10 notes + Small) with master at maximum.
- **major** — The focused layer's piano type is overwritten by the single panel value on every control press: syncFunctionalControls writes the panel type into engine.setLayerType(focusedLayer, ...) on every functional control change. After selecting Electric on layer B, pressing an unrelated effects control made B render bit-identical to clean Grand. The type LED also shows the panel value rather than the focused layer's model, so panel feedback and sounding voice disagree (panel 'Grand' while layer B renders Electric).
- **minor** — Reverb return bypasses the layer level stage and never reaches fully wet: The reverb send is tapped from the per-voice gain and returns straight to master, so with the piano level fader at minimum the dry onset drops from 0.176 to 0.050 while the tail rises slightly (0.0465 -> 0.0581 at 0.6-1.2 s), and at maximum AMOUNT the dry path is never attenuated (spec: 'Dry/Wet (fully wet at max)').
- **minor** — Effect edits never affect sounding notes: Because the chain is baked into each voice buffer, engaging Mod 1 at maximum amount 900 ms into a held note left the note's envelope perfectly smooth and unmodulated. On the hardware every unit is live on held notes; here only reverb send level, layer level and master level ride real nodes.
- **minor** — Timbre shows Dyno 1/2 on acoustic types but applies Off/Soft: The timbre button always cycles six options; on the Grand, 'Dyno 1' renders bit-identical to Off and 'Dyno 2' identical to Soft (timbre is taken modulo 4 for non-electric types), so two of six LED positions report a setting the engine does not apply.
- **minor** — FX focus does not follow layer focus and the section focus buttons are absent: The effects spec requires focus to follow layer focus plus manual Organ/Piano/Synth focus buttons. Only A/B focus buttons exist and focusSection is hard-coded to 'piano'; with layer B focused, a Mod 1 edit landed on chain A and the sounding layer stayed bit-identical to clean. Neither focus button shows a default pressed state on load.
- **minor** — Status reads 'ready (recorded sample library)' before any library is decoded: The engine reports ready at init while the recorded libraries are still fetching, so the first note after page load renders the synthesized fallback (cold rms 0.0454 / zcr 523 vs warm 0.0563 / 714 for the same key) under a status line that already claims the recorded library.

## Phase 3: Complete Stage 4 system

**68/100**

A complete, carefully engineered Stage 4: correct chassis geometry (deck 0.540, keybed 0.460, width 0.940, aspect 3.0951, worst section deviation 0.0058), an exact 73-key E1-E7 keybed (43/30, black-key height 0.610, all keys inside), 5/5 reference colours inside deltaE 12, 156/156 controls reachable at 1440x900 and 32/33 landmarks present. The arpeggiator can only run off a stale config snapshot, so it never arpeggiates in normal play.
