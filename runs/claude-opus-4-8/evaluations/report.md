### Phase 1: Complete surface and basic piano

- Audio strategy: One basic piano voice produced by honest real-time synthesis in a single Web Audio AudioContext. Each note is a small additive oscillator stack (a triangle fundamental, a slightly detuned sine for body, and sine partials at the octave and twelfth) shaped by a per-note gain envelope. Velocity scales the peak gain on a squared curve; note-off applies a per-note linear release; sustain (UI/keyboard/MIDI CC64) holds released notes until the damper lifts. All voices route through one master gain into a DynamicsCompressor acting as a soft limiter, then to the single AudioContext.destination. Polyphony is bounded (16 voices) with deterministic oldest-first voice stealing. There are NO recorded samples in this phase.
- Generated sound sources: Phase 1 basic piano voice — This is synthesized, not a recording. It is a deliberately simple, dependable placeholder for the Phase 2 recorded sample sets (Grand/Upright/Electric), which are NOT present yet.
- Recorded sample provenance: No recorded or external sample sources declared
- Bundled audio: None detected
- Audio note: No recorded sample sets are bundled in Phase 1. Grand/Upright/Electric recorded sample sets are Phase 2 scope.
- Audio note: The audio boundary is injectable (src/audio/types.ts). Tests use src/audio/fakeBackend.ts — no real AudioContext, no audio output, no network, no MIDI device.
- Audio note: If no AudioContext is available, the app enters a truthful, labeled silent 'fallback' status that still tracks the note lifecycle and never reports the primary voice as ready.
- Audio note: Every panel control other than the keybed and sustain input is honestly decorative: it moves/presses and stores presentation-only state (src/state/controlStore.ts). No decorative control produces audio or mutates program/effect/system state (honesty contract).

## Phase 1: Complete surface and basic piano

**61/100**

A complete, disciplined surface with a weak instrument behind it. The panel is the strongest part: 147 named, stable-ID controls across the six sections, 147/147 reachable on a 5x5 elementFromPoint grid and 147/147 operable by real keyboard with a visible focus ring, and the decorative boundary is provably honest - driving Master Level to 0% and toggling Piano ON while a note sounds changes the rendered signal by under 1e-8 RMS. The voice itself is thin: no decay at all (RMS 0.1404 at 0.10 s, 0.1417 at 1.70 s of a held note), a 0.61 Hz beat instead, identical peaks for a top-of-key and bottom-of-key strike, and peak sample 1.528 under 20 notes. Worse, one React defect - a provider default argument re-created on every render in useMidiInput - tears down MIDI on every render, so every MIDI note dies ~0.3 s in and CC64 sustain never holds. With no UI or keyboard sustain either, sustain is unreachable in the shipped build while IMPLEMENTATION_DETAILS.json declares it working.

### Priority issues

- **critical** — Every MIDI note is force-released one frame after note-on, and CC64 sustain with it: src/hooks/useMidiInput.ts:18 declares `provider: MidiAccessProvider | undefined = browserMidiProvider()` as a default parameter, so a new function identity is produced on every render of App. The effect's dependency array is [router, provider], so the effect tears down and re-subscribes on every render; its cleanup calls controller.disconnect() (which calls handlers.sustain(false)) and router.releaseOwner('midi'). Because a note-on itself re-renders App (activeNotes state), the note it just started is released one frame later. Measured on the published build: a MIDI note held 1500 ms is audible for ~300 ms (RMS 0.1749 at t=0.05 s, 0.0088 at t=0.30 s, 0 from t=0.35 s) and the voice counter never leaves 0; navigator.requestMIDIAccess was called 70 times in one short session.
